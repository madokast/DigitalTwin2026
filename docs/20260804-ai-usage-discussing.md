## 需求：真实时间 API

> 我们需要提供一个 API 让模型去查，从而知道现在真实的时间。

## 模糊时间的 happened_at 处理

> 当用户进行回忆的时候，给出的时间一般会是一个模糊时间，比如说早饭的时候，昨天晚上，两天前，等等。那么这个时候，Happened at 就不能用现在的时间。而是一个推测发生的时间。这么做是被允许的，比如用户说下午的时候，那样可以记录为下午 15 点钟，当然，如果可以从对话中更精确地推断出是 14 点或者 16 点的话，那就进一步精确化。如果是说两天前，且没有具体说是白天还是晚上的话，一般将时间设为那一天的 12 点。
>
> 因为我们这个系统最主要的目的是用于复盘和回顾，它不太关注精确时间，只关注用户做了什么，经历了什么，在想些什么。

## 模糊想法 vs 任务

> 当用户说，我想减肥了，我今天想早点睡，我明天想去吃好吃的，我觉得下周末一定要去旅游。这些通通都是用户的一个模糊的想法，你应该记录的是想法发生的时间，也就是用户说这句话的时间，也就是现在的时间。而且你不应该使用 to do 任务清单的功能，这个功能仅在用户明确的要求创建一个任务计划的时候才使用。

## 想法中的时间只能靠原文承载

> 想法可能包含了一个或模糊或具体的时间，在这个系统中只能靠用户的原文记录在 raw content 中，系统不支持提取出结构化的信息。因此记录好后就应该赶紧返回到对话中，和用户进行正常的交流。

## 回顾中的评价 vs 客观回忆

> 当用户进行回顾的时候，可能会包含评价性的信息，比如说中午点的黄焖鸡，味道真难吃，下次再也不要点了。一旦出现回顾，那么 happened at 一定记录为这个评价出现的时间，也就是用户发言的时间，也就是现在时间。除非用户在进行完全客观性的回忆，就比如说：中午吃了一个麻辣烫，下楼散了会步之后，就回工位上休息了。如果用户是明明确确在客观性地回忆过去发生的事情，那么 happened at 就还是按照时间发生点填写模糊时间。绝对禁止将用户的话拆分为事实和评价，存成两条记录。

## 回顾+评价的核心原则

> 这种又出现回顾又出现评价的话，最核心的原则就是禁止拆分。绝对禁止将用户中的事实和评价拆成两部分。之后的权衡则是考虑 happened at 到底是填写回顾时那个事件发生的时间，还是说现在用户评论时的事件。两种做法都有优劣，但不影响长期的回顾和复盘。用户当前的偏好是，当存在评论性语句的时候，存现在的时间。

## 记账 / 待办 / 体重：先 log text 再调专用 API

> 当用户需要记账或者说创建代办清单或者记录体重的时候。一定要先用 log text 记录用户说的完整的话，同样把 objective context 给补上去，对于 AI analysis 可加可不加。
>
> 在 log text 记录成功之后，再调用特定的 API，比如记账记录、创建待办清单、记录体重来进行记录。在这个 API 中，如果需要填用户说的原文，那么就继续填上；如果需要填写 object context 或者是 AI analysis，也一并填上，重复性的填写是被鼓励的。
>
> 注意，一定不要省略 log text。

## 回顾 / 复盘：Review API 使用流程（唯一不需要双写）

> 回顾，或者说复盘，也就是使用 Review 系列的 API，这个是唯一一个不需要双写的。
>
> 当用户说回顾一下昨天，或者说又到周末了，我们回顾一下这周。或者说今天是 8 月 1 号了，那我们回顾一下 7 月份，七月份的是忙碌的一个月啊。那么 AI 直接调用 review API 来记录这一句话。
>
> 除非用户没有给出明确的复盘的时间范围。比如用户说，我觉得应该回顾一下了。这句话太模糊了，所以使用多个 text 来进行记录。
>
> 只要用户在说回顾复盘的时候带出了明确的时间范围。那么就可以不再使用 log text 的 API，直接使用 review API。而且在复盘过程中，所有的对话都存入 review API 中，不需要再双写。
>
> 当用户没有明确指出复盘流程的时候，一般请你按照如下的原则进行：当用户说回顾一下昨天，首先你就通过 review API 来记录用户说的这段话。然后就使用 query 功能来查询 happened at 昨天，将搜索的内容按照时间顺序组织输出出来。记住你组织出来的这个时间顺序的内容是不需要保存到系统中去的，仅仅就是输出到聊天对话中。你也可以在输出后进行一些小的总结和点评。
>
> 用户可能会对这些总结和点评进行一些回复，比如直接说"你说得对"，那么你就调用 review API 进行保存，原文就是"你说得对"这 4 个字。Objective context 则详细地描写"你说得对"这 4 个字到底指的是什么内容。AI analysis 则可以根据客观背景进一步的分析。
>
> 当然，一般而言，用户不可能说的这么简单。用户可能会回顾说一些重点：背昨天确实工作太忙了，都没有时间好好吃饭。那么这个时候你也是调用 review API 进行保存。
>
> 以上是日回顾的做法。如果是周回顾、月回顾这种超过一天以上的。那么当用户开启进行回顾的时候，第一次进行 query 就只搜索所回顾的时间段内的 tag 包含 review 标签的记录，这样可以避免一次性读太多的东西。同时又能够抓住主要的信息。当然，当用户具体要求回顾的时候（比如说具体要求回顾星期三），这个时候就再根据用户具体说的时间段，进行具体的 query 和具体的信息。
>
> 至于回顾的时候用户说的话等等，还是按照日回顾一样的逻辑进行处理就行了。

## objective context 的用法

> 其实这个 objective context 的使用是很简单的。就是记住一下用户说这句话时候的上下文，因为有的时候用户说的一句话很简单，比如说：真好吃。
>
> 如果通过上下文能够知道用户到底是在说什么，那么在这个 objective context 里面就可以详细地写出来。比如说：
> 1. 他可能是在指用户正在吃东西，评价为"真好吃"；
> 2. 也可能是用户在回忆他很想吃的一个零食，然后说了一句"真好吃"。
>
> 那么，当"真好吃"这三个字真的莫名其妙地被用户说出来，没有任何上下文的时候，objective context 也就如实描述：用户突然说"真好吃"这三个字，没有明确的指代。
