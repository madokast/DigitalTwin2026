# 系统设计哲学（AI 全权操作 + 前端纯展示）

> 创建日期：2026-08-05
> 性质：顶层设计原则，作为后续所有前端 / API / 权限决策的判据。
> 触发：讨论补 tag、编辑能力、admin 操作定位时，用户明确系统未来形态。

## 1. 系统未来形态

- **无直接人工操作通道**：系统 100% 由 AI 使用。人通过**对话**让 AI 操作系统，AI 调用 API。
- **前端仍存在，但定位为纯展示层**：如体重趋势折线图、记账统计、记录列表——打开前端即可查看，无需每次都让 AI 画图。
  - 前端**只读**，不做任何写操作（无表单提交、无编辑按钮、无管理操作）。
- **admin 基本不用**：系统成熟后 admin 操作极少；admin 端点是给 AI 通过 token 调用的能力，不是给人开的后门。

## 2. 核心哲学：变更来源一致性

- **所有写操作（含修改）都经由 AI 发起**，AI 是数据变更的唯一来源。
- 理由：若人绕过 AI 直接改数据（如改某 uuid 记录的字段），AI 下次读取时会**困惑**——「这个 uuid 的记录为什么变了？我没改过」。全部经 AI 操作，AI 的世界模型自洽，不会困惑。
- 推论：
  - 前端不做任何写操作（见 §1），杜绝「人绕过 AI」的变更来源。
  - 删除/编辑/补 tag 等写能力是给 AI 的 API，前端无入口。

### 2.1 推论：错误信息透传（AI 诊断权）

- **AI 是全权操作者，有权看到实际发生的错误**——系统实际存在的错误信息（DB 空间满、连接超限、查询失败的具体 message / SQLSTATE）不应被替换成固定文案（如 `Internal server error`）吞掉；否则 AI 无从诊断、无法对症行动，违背「AI 全权操作」前提。
- 推论：
  - 500 等内部错误的响应 `detail` 应**透传实际错误信息**，而非固定文案。
  - 现有行为「错误进日志但响应换固定文案」（`writeInternalError` 丢弃 err；`TestWriteInternalErrorNeverExposesDetails` 守卫）**违反本原则**，需改造为透传（双端对齐、契约 / OpenAPI 同步、守卫测试改造）。
  - 日志（slog/pino）仍保留，但**不能以「已记日志」为理由剥夺 AI 的诊断信息**。
- 安全让位于 AI 全权操作：个人系统 + AI 唯一操作者，内部错误信息（表名 / SQLSTATE）不构成威胁；若未来暴露给外部再评估。

## 3. 放开「AI 不能修改」原则

- **推翻** `docs/20260805-status-analysis.md` §1 记录的「PATCH 编辑 API 彻底删除」——该决策基于「日志不应编辑」的旧假设；新形态下 AI 可修改数据。
- **容错靠备份还原**：AI 操作失误导致数据问题时，通过**备份还原**解决，不靠限制 AI 权限。
- 保留的数据完整性约束（非权限，是结构/聚合依据）：
  - **待办状态机**：`todo:*` 四态 + transition 审计链，禁止绕过 transition 直接改状态 tag。
  - **保留前缀**：`body:weight` / `transaction_entry:*` / `review:*` 是聚合/统计依据（体重 dashboard、记账聚合、review 检索），禁止随意修改。
- 实际可修改的：普通 tag 的增删与归一化（见 §5 修改 API 清单）；**四字段（raw_content / objective_context / happened_at / ai_analysis）不可改**（追加式纠正）。

## 4. 对各能力的定位影响

| 能力 | 定位 |
|---|---|
| 前端 | 纯读展示，无写操作 |
| `log/*` 写入 | AI 通过对话发起 |
| 补 tag / 删 tag（`docs/20260805-tags-add.md`） | 搜索辅助；任意记录 + 任意时间；给 AI 用，前端无入口 |
| 编辑 API（PATCH） | **不复活**——见 §5，修改在系统中实际价值极低 |
| tag 归一化（normalize） | 全表合并，搜索规范化；见 `docs/20260805-tag-design.md` |
| admin 端点（normalize / import） | AI 经 token 调用；前端不暴露 |
| 备份 | 容错兜底，替代「限制权限」作为风险控制 |

## 5. 修改在系统中实际价值极低（核心结论）

**系统目的** = 复盘/回顾，只关注「做了什么、经历了什么、想了什么」；时间只是粗粒度索引。

**推演链（重要结论）**：
1. **时间模糊不是错误**：系统只需把记录归入「大致的时间段」（天/周/月），模糊时间（「今天上午」记 10:00）在段归属上几乎总是正确，够用。
2. **时间偏移一格影响极小**：辞职记在 7/31 还是 8/1，复盘结论几乎不变——相邻月都会提到该事件，只是表述位置不同；复盘关心「发生了什么、意义、感受」，不依赖精确日历位置。
3. **边界不需要精确化**：「23:59→00:00」与「12:57→12:58」在物理上无本质区别，日历分段是人为工具；边界错一条不影响「忙碌的一周」这类语义结论。
4. **四字段均不需修改**：`happened_at`/`raw_content`/`objective_context`/`ai_analysis`——写错用**新记录追加纠正**（旧哲学），不修改旧记录。
5. **PATCH 不复活**：既然修改价值极低，通用编辑 API（PATCH）无需恢复。

**结论**：系统对时间精度要求 = 大致归入周/月段即可。**修改在系统中价值极低，保持日志不可变 + 追加式纠正**。

### 修改 API 最终清单（收敛）

修改（非追加写入）类 API **仅两种**，其余全部不提供：

| 操作 | 鉴权 | 风险 | 收益 | 说明 |
|---|---|---|---|---|
| 给单条记录加/删一个 tag | ApiToken | 低 | 搜索辅助 | `docs/20260805-tags-add.md`；单 id + 单 tag；普通 tag 可增删，保留前缀禁 |
| 整体 tag 归一化（normalize） | AdminToken | **最大**（全表） | **最高**（搜索规范化） | 多源→单目标；合并 `exercise`/`workout` 等避免双重搜索；系统最大风险点；见 `docs/20260805-tag-design.md` |

不提供的修改能力：
- ❌ PATCH / 通用字段编辑（四字段均不可改）
- ❌ 时间修改
- ❌ 删记录

容错：AI 操作失误靠备份还原兜底。

### 时间模糊标记（不强制）

- 系统**不内建**「时间模糊」语义——AI 可选择标记（自由命名，如 `time:estimated`）、可自由选择方式、甚至不标记；**不设保留前缀**。
- 理由：标记收益极低（模糊时间段归属大多正确），强制标记反而增加 AI 负担、限制 AI 的合理自由发挥。
- 若 AI 需要，用普通 tag 即可（可加可删，走 tags 编辑接口）。
