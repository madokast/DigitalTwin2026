## 1. 本日议题：模糊时间

### 1.1 背景

7 月 27 号讨论中已提出"模糊时间"（§4.3），但当时未拍板。今天确认这是一个**核心问题**而非边角。

原因：当前**没有实时监控设备**捕捉我的各种行为，大量记录是事后回顾。例如：

- "昨天晚上大概是 24 点、凌晨前后睡的觉" —— 没有确切入睡时间
- "今天早上醒来大概是 7:50 左右" —— 也是大约

这种模糊性是**常态**而非例外。如果系统无法表达模糊时间，要么逼用户编造精确值（污染数据），要么放弃记录（丢数据）。

### 1.2 模糊时间的几种形态（待补充）

- **带不确定度的点**：如"7:50 左右" —— 中心 + 误差范围（如 ±10 分钟）
- **区间但边界本身也模糊**：如"凌晨前后睡的" —— 大约在 23:30~00:30 之间
- **仅相对描述，无具体时刻**：如"晚饭后"、"睡前" —— 无任何时钟值，只有事件间序关系
- **缺失**：只记得"昨天某时"，连粗略时段都没有

### 1.3 候选表达方案（已被 §1.5 否决，保留作历史记录）

- **A. 字符串原样存**：每次统计都要 AI 解析（S7 同源问题）。
- **B. 区间表达**：丢失"中心倾向"，时长会失真。
- **C. 中心 + 误差**：字段多，只能描述点模糊。
- **D. 复合存**：区间 + 中心/置信度，最不"省"。
- **E. 概率/分布**：表达力强但最重。

> 上述五方案均被 §1.5 的认识推翻。

### 1.5 讨论后的转向：模糊时间直接存成精确时间

讨论中出现一个关键认识，推翻了 §1.3 的所有候选方案：

- **结论：模糊时间就当作精确时间来存。**
  - 如"大概 8 点" → 存 `08:00`；
  - "凌晨前后睡的" → 存一个具体时刻（如 `00:00`）。
- 曾考虑加布尔字段标记"精确/模糊"，但意识到**逐条标记没有意义**：
  - 事后回顾的数据，真实时间找不回了；
  - 后续处理（统计、排序、时长计算）只能把这些值当成确切时间用，无法利用标记做任何特殊处理；
  - 逐条标记本身不改变数据被使用的方式，纯属噪音。
- 因此：**不引入逐条模糊/精确标记字段，不存区间，不存分布。一个时间就是一个时间戳，AI 录入时自行把模糊描述"塌缩"到一个具体时刻。**

### 1.6 字段语义契约：需知"可能不精确"

虽然不做逐条标记，但有一条**字段级语义契约**需要让用户和 AI 都知道：

- 该时间字段的取值，**可能是从模糊描述塌缩而来的精确时间点，并非都是真实测得的精确值**。
- 这条信息以**契约/文档形式**承载，不进数据库逐条标记：
  - 对**用户**：在 UI 文档/说明里写明，避免误以为所有时间都是精确测量；
  - 对 **AI**：在录入工具/接口的描述里写明，让 AI 在后续读取、统计、解释该字段时，心里有数（例如解释统计结果时不要把精度说得过于确定）。
- 一句话：**"知道这一点"靠 schema 契约，不靠逐条数据。**

### 1.7 塌缩规则

AI 把模糊时间塌缩成精确值时，**不做硬约束，交给 AI 自由判断**——它根据上下文选最合理的点（可能取区间中心、可能取提到的最具体时刻、可能就近整点）。

约束只到"塌缩后必须是一个具体时间戳"这一层，不规定具体算法，避免把规则拆得太碎反而让 AI 不知所措。

### 1.8 原文冗余原则：value_text 必须保留最原始发言

塌缩、抽取出来的字段（时间、数值等）与原文是**冗余并存**关系，不是"拆走就删"。

**反例（禁止）**：
用户说"今天早上睡了个懒觉，9 点多了才醒的"。
- 错误做法：把"9 点"抽到 `happened_at`，`value_text` 只剩"今天早上睡了个懒觉，才醒的"——把"9 点"从文本里删掉。
- 这样不行。

**正例（要求）**：
- `happened_at` 存 `09:00`（塌缩后的精确值）
- `value_text` 仍存用户最原始发言全文："今天早上睡了个懒觉，9 点多了才醒的"

**两条理由**：
1. **可回顾追溯**：原始发言本身有留存价值，是"我"在那一刻的真实表达，含语气、措辞、细节，不是单纯的数据源。
2. **避免语义被拆散后失真**：把某些信息从文本里"抠走"，剩下的文本可能语义就变了，甚至变得不通顺；保留原文，保证语义完整。

**推论**：
- `value_text` 存的是**用户原始发言**，不是 AI 加工/裁剪后的版本；
- 时间字段、数值字段是对原文的"额外抽取"，与原文并存，不替代原文；
- 这与 §1.6 的"字段可能不精确"相呼应——塌缩值是衍生品，原文才是"事实"，二者冗余存。

### 1.9 原文保真的强度（约定，非硬约束）

`value_text` 不仅是"存原文"，而是**约定逐字保真**：

- 不删语气词（"嗯"、"吧"、"那个"）；
- 不修正小错误（口误、错字、语病）；
- 不做任何规范化或润色。

**唯一例外**：AI 对语义不理解时，**不去自行修正或猜测**，而是**回头向用户追问清楚**，等用户给出明确表达后再原样存入。

> 这意味着：AI 的工作不是"清洗用户输入"，而是"理解 → 必要时追问 → 抽取衍生字段 → 原文一字不改地入库"。

**⚠️ 执行层面的现实**：

- 整条记录是 AI 写进去的，AI 是否如实转录，**没有 hook 能验证**；
- 用户说的话在对话里，AI 写进 DB 的是它自己生成的文本，二者是否一致只能靠 AI 自觉；
- 如果 AI 改了语气词、做了轻度润色、甚至无意中换了措辞，事后无法察觉（除非用户逐字对照聊天记录和 DB 内容）。

**因此"逐字保真"是写给 AI 的工具描述里的一句指令/约定，不是 schema 约束，不能强校验。** 与 §7.3 靠 AI 自觉去重 tag 同性质——指令要严格，能影响多少算多少；schema 层面承认不能强校验。

## 2. 字段存储类型

### 2.1 总原则

- 尽可能用 **SQL 标准类型**，避免厂商特有功能，便于跨数据库切换；
- 不用 PG 特有的 `text[]` 数组，改用 SQL 标准的 JSON 存 tag 数组；
- `TIMESTAMPTZ` 即 SQL 标准的 `TIMESTAMP WITH TIME ZONE`，可用。

### 2.2 三个时间字段，按语义区分存储方式

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `recorded_at` | `BIGINT`（Unix epoch，秒或毫秒待定） | 系统写入时刻，纯绝对时刻，无"用户当地体验"要保留；用整型存最通用、跨库无差异（连 SQLite 都没问题） |
| `happened_at` | `TIMESTAMP WITH TIME ZONE` | 用户表达的事件时间，含"7:50 醒的"这种本地时区语义；带时区才能既存绝对时刻又保留当地体验 |
| `happened_until` | `TIMESTAMP WITH TIME ZONE` | 同上，时间段结束点 |

### 2.3 为什么 recorded_at 用整型、happened_* 用时间类型

- `recorded_at` 是系统生成的、无地理语境的绝对时刻，bigint 足矣；
- `happened_*` 承载"用户在当地 7:50 醒的"这种本地体验，必须带时区，否则旅行跨时区时数据会错位；
- 区分存储让"标准且通用"在 recorded_at 上贯彻得更彻底，happened_* 用标准时间类型也不破坏可移植性。

### 2.4 时区"不乱"的具体含义

存"7:50 醒的"：
- **不带时区**：北京 7:50 和东京 7:50 是两个不同的绝对时刻，但存进去都变 "07:50"，无法区分；跨时区统计时旅行那几天会和本地数据混在一起、时段错位。
- **带时区**（如 `07:50+08`）：绝对时刻不歧义（同一个 UTC instant），跨时区排序、跨日分桶不会错位；原始本地时间也能还原（按当时当地时区展示，"你那时是 7:50 醒的"体验被保留）。

一句话：带时区 = 绝对时刻 + 本地体验两头都不丢。

### 2.5 tag 数组改用 JSON

记录表的 `tags` 字段：
- 类型：标准 SQL JSON（SQL:2016 起标准化），PG / MySQL / SQLite 较新版本均支持；
- 内容：字符串数组，如 `["工作","学习","source:device"]`；
- 放弃 PG 专有的 `text[]`，换取跨库可移植性；
- 查询时用各库的 JSON 操作符展开/包含判断，可接受。

### 2.6 仍待定

- [ ] `recorded_at` 用秒还是毫秒精度？（倾向秒，对模糊时间为主的系统够用）
- [ ] JSON 在不同库的行为差异是否需要在应用层做一层封装？
- [ ] `id` 字段用 `BIGINT` 自增还是 UUID？（跨库迁移时 UUID 更友好）

## 3. 部署分析：Vercel + Neon

> 暂停表设计，先讨论部署。如不行再换。

### 3.1 选型

- 应用层：**Vercel**（Next.js 原生部署，与 `.gitignore` 已确定的栈一致）
- 数据库：**Neon**（serverless PostgreSQL，原生支持 §2 的时间类型与 JSON）
- 协议：AI 与后端走 **HTTP POST**，放弃 MCP（见 §3.3）

### 3.2 契合度分析

| 维度 | Vercel + Neon 是否满足 |
| --- | --- |
| Next.js 栈 | ✅ Vercel 是 Next.js 原生平台 |
| PostgreSQL | ✅ Neon 是真 PG，`TIMESTAMP WITH TIME ZONE` / JSON / UUID 都原生支持 |
| 量级 | ✅ 免费够用：Neon 0.5GB + 60 compute 小时/月；10 万条记录 + 索引几十 MB；Vercel 函数 100 万调用/月 |
| 连接池 | ✅ Neon 自带 pooler，适配 Vercel serverless 的"短连接多"模式（serverless + PG 最易踩的坑） |
| 函数超时 | ✅ 免费 10s / Pro 60s；本项目接口都是"插一条记录"毫秒级，无压力 |

### 3.3 MCP 这条线放弃

- MCP server 通常是常驻进程，Vercel 是无状态 serverless，二者不匹配；
- 改走"AI 调普通 HTTP POST"，与昨天 §8 的"LLM 调 HTTP POST 到后端"一致；
- 即 LLM 端用 function calling，工具的实现是一个 HTTP 客户端调用 Vercel 上的 Route Handler，不需要常驻 MCP server。

### 3.4 可能踩到的坑

1. **后台任务**：将来若需要"每日自动统计推送给 AI"这类常驻 worker，Vercel 不能跑——需用 Vercel Cron（免费每天一次）或外挂。
2. **冷启动**：Neon 闲置后会 suspend 计算，下次查询有 ~1s 延迟；个人项目可接受。
3. **Vercel 函数无状态**：不能依赖进程内缓存、长连接；每次请求都是独立函数调用。

### 3.5 结论

**Vercel + Neon 可行，直接走这条。**

- 协议定为 HTTP（非 MCP）；
- 后端即 Next.js Route Handlers；
- 后续若发现 v1 后台任务需求膨胀，再考虑外挂 worker 或换部署平台。

### 3.6 Vercel 免费（Hobby）额度实查

| 项目 | 免费额度 | 本项目预计用量 |

## 4. 具体使用场景与动机

### 4.1 当前已走通的工作流

- 我与 AI 聊天，让 AI 记录信息；
- 目前 AI 把记录写到**本地 Markdown 文件**。

### 4.2 现在想做的事

把存储从"本地 Markdown"迁移到"HTTP → 数据库"。

### 4.3 迁移动机

1. **比文件好分析**：数据库有结构化字段（数值、时间、tag），可 SQL 查询、聚合；Markdown 要靠 AI 重新解析，成本高且不稳定（与 S7 同源问题）。
2. **容易做统计**：体重趋势、睡眠时长、时间分配等统计，在数据库里是简单 SQL；在 Markdown 里要么靠 AI 每次重新读，要么额外写解析器。

### 4.4 含义

- v1 的核心是"把已走通的 Markdown 记录迁移到 DB"，不是从零做新功能；
- AI 仍是唯一录入入口（见昨日 §8），只是写入目标从文件改成 HTTP；
- 用户侧体验不变，仍是和 AI 对话。

### 4.5 现有 Markdown 样本分析

> 样本：`2026-07-26.md`（用户提供）

**现有格式**
- 每行：`HH:MM - <内容>`
- 时间：记录写入时刻（对应 `recorded_at` 语义）
- 内容：AI 对 MDK 发言的转述/总结，非原文

**样本片段示例**
```
18:00 - MDK 说快到中午才起来，昨天睡太晚了，和小月黑白颠倒有关系。又一次印证了 lesson 4：小月的作息会拖垮他的睡眠。
18:38 - MDK 纠正：其实吃了不少——400ml 酸奶 + 400g 吐司。下午觉得冷的主因不是吃的少，而是长时间专注数学物理没动，身体处于低活动状态。我之前的判断偏了。
```

**与现有设计的差距**

| 维度 | 现状 | 设计要求（见 §1.8/§1.9/S7） | 差距 |
| --- | --- | --- | --- |
| 原文保真 | AI 转述/总结 | 约定逐字保真（§1.9，软约束） | ⚠️ 软约束，无法强校验 |
| 数值提取 | 埋在文本里（"400ml 酸奶"） | 抽到 `value_numeric` | ❌ 违反 S7 |
| tag | 无 | 应有内容 tag（学习/睡眠/社交…） | ❌ 缺失 |
| AI 评论 | 与事实混在一起（"我之前的判断偏了"） | ？未定义 | ⚠️ 待定 |
| 重复行 | AI 多次重新总结同一件事 | 一条记录一次入库 | ⚠️ 待定 |

**暴露出的新问题**

1. **AI 的评论/分析算不算"记录"？**
   - "值得肯定"、"我之前的判断偏了"、"纠正了我之前的判断"——这些是 AI 的衍生分析，不是 MDK 的事实；
   - 入库会污染事实层；不入库又丢失了 AI 的判断过程。

### 4.6.1 AI 评论字段：ai_comment

**结论：新增 `ai_comment` 字段（文本，可空），与 `value_text` 分列存放。**

- `value_text` —— 用户原始发言，逐字保真（§1.9）
- `ai_comment` —— AI 的评论/分析/判断，依附于同一条记录

**为什么单独字段而不是独立记录**：
- AI 评论总是依附于某条用户发言，强绑定关系；
- 拆成独立记录会让 AI 评论混进统计（如统计睡眠时长时把"值得肯定"也算进去）；
- 分列存放：查事实看 `value_text`，查 AI 分析看 `ai_comment`，干净。

**ai_comment 也逐字保真，不重新生成**：
- AI 评论同样是"那一刻的表达"，与 `value_text` 同等对待；
- 若 AI 理解错了，**用户说出来作为一条新记录 append**（遵循 §4.6 append-only），而不是让 AI 重新生成评论；
- 重新生成具有不确定性，append 新记录是确定且可追溯的。

> 一句话：原文与 AI 评论都保真，错误都靠 append 勘误，不靠重新生成。

### 4.6.2 一次发言拆不拆记录，由 AI 自行判断

**问题**：用户一次发言可能含多个不相关事实（如"睡到 9 点，晚饭吃了面条"），AI 该拆成多条还是记一条？

**结论：不硬性规定，让 AI 自己判断。**

- 允许拆：当发言里多个事实毫不相关时，AI 可拆成多条记录，每条打对应 tag；
- 允许不拆：当事实关联较紧或拆分代价过大时，AI 可记成一条，打多个 tag；
- 不写 hook 校验拆分粒度——与 §1.9 同性质，属 AI 自主范畴，用户控制不了。

**与已有设计的关系**：
- 不强制拆 ↔ 不强制合，二者并存，由 AI 根据语义自行裁量；
- 不引入 `parent_id` / 关联字段（违反 §7.5 能省则省）；
- 拆与不拆都不影响原文保真（§1.9）：拆的情况下，每条记录的 `value_text` 是该事实对应的用户原话片段；不拆则整段原话入库。

> 一句话：拆不拆是 AI 的判断权，不是 schema 约束。

## 5. 系统定位的重大转向：观察日志 + 无前端

### 5.1 重新定位

经过讨论，记录的本质重新定位为：

- **观察日志**：AI 与用户交流，观察其所作所为、所思所想，客观记录下来；
- **黑匣子**：用户几乎不会主动去读 DB 原文；
- **AI 是唯一读者**：所有查询、统计、分析，都通过 AI 转手——AI 查数据库 → 分析 → 用自然语言告诉用户。

### 5.2 含义

- **不需要前端 UI**：v1 可以无前端展示，用户交互全在 AI 对话里完成；
- 用户问题示例：
  - "上个月工作做了些什么？"
  - "今年来的体重趋势是什么？"
  - "最近的情绪是否稳定？"
- 这些都由 AI 查询 DB（SQL 或调用查询接口）→ 分析结果 → 自然语言回答用户。

### 5.3 对已有设计的影响

| 设计项 | 影响 |
| --- | --- |
| §1.8 原文冗余 | **仍成立**——AI 是读者，原文冗余让 AI 既能看衍生字段又能看原文，更准 |
| §1.9 逐字保真 | **仍成立**——前端要展示原文给用户看，逐字保真仍有意义；待磨合期后再考虑松动 |
| §4.6.1 `ai_comment` | **仍成立且更重要**——用户不读原文，AI 评论/上下文补全成为 AI 自己后续理解的依据 |
| §4.6 append-only | **仍成立** |
| §4.5 历史迁移 | **可降优先级**——既然用户不读原文，历史 Markdown 留着也无妨，新数据进 DB 即可 |
| 前端 UI | **v1 仍需**——至少能看原文，作为磨合期检视与调试用；待磨合完成后再考虑移除 |
| 查询接口 | **必做**——AI 需要能查 DB（按 tag、时间区间、数值范围等） |

### 5.4 v1 范围（修正）

原计划：录入接口 + 存储表 + 前端展示
新计划：**录入接口 + 存储表 + 查询接口 + 简易前端（看原文）**

- 录入：AI 调 HTTP POST，append 一条记录
- 查询：AI 调 HTTP GET（参数化查询）
- 前端：能看原文，最小化展示层（磨合期工具）

### 5.5 录入接口形态（按三类分）

**录入按语义拆成三个接口：**

| 接口 | 主要 payload | 用途 |
| --- | --- | --- |
| `POST /log/numeric` | `value_numeric` + tag + 时间 | 记录数值（体重、血压、心率…） |
| `POST /log/text` | `value_text` + tag + 时间 | 记录自然语言（行为、心情、思考…） |
| `POST /log/interval` | `happened_at` + `happened_until` + tag + 描述 | 记录时间段（睡眠、工作时段…） |

**为什么按语义拆而不是单一通用接口**：
- 每个接口参数更聚焦，AI 调用时意图明确，减少错填概率；
- 与"AI 录入受 schema 约束"（S7）一致：接口形态本身即在引导 AI 把数值塞数值字段、文本塞文本字段；
- 三个接口对应三种主要数据形态，与 §7.2 表字段设计一致。

### 5.6 查询接口形态（也按三类分）

**查询也对应拆成三个接口：**

| 接口 | 用途 |
| --- | --- |
| `GET /query/numeric` | 查数值类记录（按 tag、时间区间） |
| `GET /query/text` | 查文本类记录（按 tag、时间区间、全文关键词） |
| `GET /query/interval` | 查时间段类记录（按 tag、时间区间，含时长统计） |

**关键决策：不分专题视图给 AI**

- 否决方案：按维度建视图（`v_weight`、`v_blood_pressure`、`v_heart_rate`…），每加一个新维度都要建新视图；
- 选用方案：AI 自己用 tag 区分维度（如查体重就 `tag=体重`），不需要为每个生理指标单独建视图；
- 这与 §7.3 "一切皆 tag" 的取向一致——维度靠 tag 表达，不靠表/视图结构。

**表结构隐藏**：
- 三个查询接口都返回结果集，不暴露底层表结构与字段名；
- AI 看到的是"按 tag 和时间过滤后的记录列表"，而非 SQL schema；
- 用户对暴露表结构的顾虑由此化解。

### 4.6 记录只增不删改（append-only）

**原则：不向 AI 提供 UPDATE/DELETE 接口，AI 只能 POST 新记录。**

- AI 发现错误时，**不修改原记录**，而是**新增一条记录**，在 `value_text` 里用自然语言说明"上一条错了/实际是……"。
- AI 在后续读取/统计时，自行结合勘误记录理解真实情况，与人类看日记勘误的方式一致。

**例外：人类可以直接改数据库**

- 上述 append-only 是对 **AI 接口层面**的约束，不是数据库层面的硬约束；
- 当错误**会外溢影响统计**时（如 tag 语义重复导致聚合错乱），用户会**直接介入数据库**修正；
- 当错误**仅是单条事实层的小错**（如一句话说错了），则遵循 append-only，用新增勘误记录处理，不去改原记录。

**判断准则**：
- 错误影响范围仅限该条记录自身 → append-only，用勘误记录处理；
- 错误会污染跨记录的统计/聚合 → 用户直接改库。

**对其他设计的影响**：
- §7.3 标签改名/合并走全表 UPDATE：**仍成立**——这正是"会影响统计的错误"，由用户直接改库修正，而非 AI 通过接口操作；
- §1.9 原文逐字保真：仍成立（作为给 AI 的约定）——AI 不能改原文，但用户可以；
- 简化 AI 接口：录入接口只有 POST，AI 侧没有 UPDATE/DELETE。

> 关键澄清：append-only 不是"数据库永远不可改"，而是"AI 接口不提供改的口子"。人与 AI 的权限不对称。
