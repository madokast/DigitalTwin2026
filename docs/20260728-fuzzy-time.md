## 1. 本日议题：模糊时间

### 1.1 背景

7 月 27 号讨论中已提出"模糊时间"（§4.3），但当时未拍板。今天确认这是一个**核心问题**而非边角。

原因：当前**没有实时监控设备**捕捉我的各种行为，大量记录是事后回顾。例如：

- "昨天晚上大概是 24 点、凌晨前后睡的觉" —— 没有确切入睡时间
- "今天早上醒来大概是 7:50 左右" —— 也是大约

这种模糊性是**常态**而非例外。如果系统无法表达模糊时间，要么逼用户编造精确值（污染数据），要么放弃记录（丢数据）。

### 1.2 模糊时间的几种形态（待补充）

- **带不确定度的点**：如"7:50 左右" —— 中心 + 误差范围（如 ±10 分钟）
- **区间但边界本身也模糊**：如"凌晨前后睡的" —— 大约在 23:30~00:30 之间
- **仅相对描述，无具体时刻**：如"晚饭后"、"睡前" —— 无任何时钟值，只有事件间序关系
- **缺失**：只记得"昨天某时"，连粗略时段都没有

### 1.3 候选表达方案（已被 §1.5 否决，保留作历史记录）

- **A. 字符串原样存**：每次统计都要 AI 解析（S7 同源问题）。
- **B. 区间表达**：丢失"中心倾向"，时长会失真。
- **C. 中心 + 误差**：字段多，只能描述点模糊。
- **D. 复合存**：区间 + 中心/置信度，最不"省"。
- **E. 概率/分布**：表达力强但最重。

> 上述五方案均被 §1.5 的认识推翻。

### 1.5 讨论后的转向：模糊时间直接存成精确时间

讨论中出现一个关键认识，推翻了 §1.3 的所有候选方案：

- **结论：模糊时间就当作精确时间来存。**
  - 如"大概 8 点" → 存 `08:00`；
  - "凌晨前后睡的" → 存一个具体时刻（如 `00:00`）。
- 曾考虑加布尔字段标记"精确/模糊"，但意识到**逐条标记没有意义**：
  - 事后回顾的数据，真实时间找不回了；
  - 后续处理（统计、排序、时长计算）只能把这些值当成确切时间用，无法利用标记做任何特殊处理；
  - 逐条标记本身不改变数据被使用的方式，纯属噪音。
- 因此：**不引入逐条模糊/精确标记字段，不存区间，不存分布。一个时间就是一个时间戳，AI 录入时自行把模糊描述"塌缩"到一个具体时刻。**

### 1.6 字段语义契约：需知"可能不精确"

虽然不做逐条标记，但有一条**字段级语义契约**需要让用户和 AI 都知道：

- 该时间字段的取值，**可能是从模糊描述塌缩而来的精确时间点，并非都是真实测得的精确值**。
- 这条信息以**契约/文档形式**承载，不进数据库逐条标记：
  - 对**用户**：在 UI 文档/说明里写明，避免误以为所有时间都是精确测量；
  - 对 **AI**：在录入工具/接口的描述里写明，让 AI 在后续读取、统计、解释该字段时，心里有数（例如解释统计结果时不要把精度说得过于确定）。
- 一句话：**"知道这一点"靠 schema 契约，不靠逐条数据。**

### 1.7 塌缩规则

AI 把模糊时间塌缩成精确值时，**不做硬约束，交给 AI 自由判断**——它根据上下文选最合理的点（可能取区间中心、可能取提到的最具体时刻、可能就近整点）。

约束只到"塌缩后必须是一个具体时间戳"这一层，不规定具体算法，避免把规则拆得太碎反而让 AI 不知所措。

### 1.8 原文冗余原则：value_text 必须保留最原始发言

塌缩、抽取出来的字段（时间、数值等）与原文是**冗余并存**关系，不是"拆走就删"。

**反例（禁止）**：
用户说"今天早上睡了个懒觉，9 点多了才醒的"。
- 错误做法：把"9 点"抽到 `happened_at`，`value_text` 只剩"今天早上睡了个懒觉，才醒的"——把"9 点"从文本里删掉。
- 这样不行。

**正例（要求）**：
- `happened_at` 存 `09:00`（塌缩后的精确值）
- `value_text` 仍存用户最原始发言全文："今天早上睡了个懒觉，9 点多了才醒的"

**两条理由**：
1. **可回顾追溯**：原始发言本身有留存价值，是"我"在那一刻的真实表达，含语气、措辞、细节，不是单纯的数据源。
2. **避免语义被拆散后失真**：把某些信息从文本里"抠走"，剩下的文本可能语义就变了，甚至变得不通顺；保留原文，保证语义完整。

**推论**：
- `value_text` 存的是**用户原始发言**，不是 AI 加工/裁剪后的版本；
- 时间字段、数值字段是对原文的"额外抽取"，与原文并存，不替代原文；
- 这与 §1.6 的"字段可能不精确"相呼应——塌缩值是衍生品，原文才是"事实"，二者冗余存。

### 1.9 原文保真的强度（约定，非硬约束）

`value_text` 不仅是"存原文"，而是**约定逐字保真**：

- 不删语气词（"嗯"、"吧"、"那个"）；
- 不修正小错误（口误、错字、语病）；
- 不做任何规范化或润色。

**唯一例外**：AI 对语义不理解时，**不去自行修正或猜测**，而是**回头向用户追问清楚**，等用户给出明确表达后再原样存入。

> 这意味着：AI 的工作不是"清洗用户输入"，而是"理解 → 必要时追问 → 抽取衍生字段 → 原文一字不改地入库"。

**⚠️ 执行层面的现实**：

- 整条记录是 AI 写进去的，AI 是否如实转录，**没有 hook 能验证**；
- 用户说的话在对话里，AI 写进 DB 的是它自己生成的文本，二者是否一致只能靠 AI 自觉；
- 如果 AI 改了语气词、做了轻度润色、甚至无意中换了措辞，事后无法察觉（除非用户逐字对照聊天记录和 DB 内容）。

**因此"逐字保真"是写给 AI 的工具描述里的一句指令/约定，不是 schema 约束，不能强校验。** 与 §7.3 靠 AI 自觉去重 tag 同性质——指令要严格，能影响多少算多少；schema 层面承认不能强校验。

## 2. 字段存储类型

### 2.1 总原则

- 尽可能用 **SQL 标准类型**，避免厂商特有功能，便于跨数据库切换；
- 不用 PG 特有的 `text[]` 数组，改用 SQL 标准的 JSON 存 tag 数组；
- `TIMESTAMPTZ` 即 SQL 标准的 `TIMESTAMP WITH TIME ZONE`，可用。

### 2.2 三个时间字段，按语义区分存储方式

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `recorded_at` | `BIGINT`（Unix epoch，秒或毫秒待定） | 系统写入时刻，纯绝对时刻，无"用户当地体验"要保留；用整型存最通用、跨库无差异（连 SQLite 都没问题） |
| `happened_at` | `TIMESTAMP WITH TIME ZONE` | 用户表达的事件时间，含"7:50 醒的"这种本地时区语义；带时区才能既存绝对时刻又保留当地体验 |
| `happened_until` | `TIMESTAMP WITH TIME ZONE` | 同上，时间段结束点 |

### 2.3 为什么 recorded_at 用整型、happened_* 用时间类型

- `recorded_at` 是系统生成的、无地理语境的绝对时刻，bigint 足矣；
- `happened_*` 承载"用户在当地 7:50 醒的"这种本地体验，必须带时区，否则旅行跨时区时数据会错位；
- 区分存储让"标准且通用"在 recorded_at 上贯彻得更彻底，happened_* 用标准时间类型也不破坏可移植性。

### 2.4 时区"不乱"的具体含义

存"7:50 醒的"：
- **不带时区**：北京 7:50 和东京 7:50 是两个不同的绝对时刻，但存进去都变 "07:50"，无法区分；跨时区统计时旅行那几天会和本地数据混在一起、时段错位。
- **带时区**（如 `07:50+08`）：绝对时刻不歧义（同一个 UTC instant），跨时区排序、跨日分桶不会错位；原始本地时间也能还原（按当时当地时区展示，"你那时是 7:50 醒的"体验被保留）。

一句话：带时区 = 绝对时刻 + 本地体验两头都不丢。

### 2.5 tag 存储：以文本方式存 JSON

记录表的 `tags` 字段：
- 类型：**普通 `TEXT`**，存 JSON 字符串（如 `["工作","学习","source:device"]`）；
- 不用 PG 专有的 `jsonb`，也不用 SQL 标准的 JSON 类型——纯文本最通用，跨库无差异；
- 与 §2.1 "尽可能用 SQL 原生标准"取向高度一致：`TEXT` 是所有数据库都支持的最基础类型。

**关键约束：tag 值内部不能含双引号 `"`**。

理由与好处：

- 模糊搜索：直接对文本字段做 `LIKE '%关键词%'`，无需 JSON 解析；
- 精确搜索（按 tag 精确匹配）：搜索 `"tag名"`（带双引号）即可——JSON 中每个 tag 都被双引号包裹，`LIKE '%"tag名"%'` 即可命中且不会误匹配子串（如搜 `"新"` 不会命中 `"新学习"`，因为有闭合双引号作边界）；
- 由于 tag 本身是简单标签（如 `工作` / `review:weekly` / `source:device`），禁止双引号是合理约束；
- 应用层负责序列化（数组 → JSON 字符串）与反序列化。

**推论**：
- 所有要存进 `tags` 的字符串（tag 名）必须不含双引号——含则需先转义或拒绝；
- §5.7 查询接口的 `q` 参数对 `tags` 字段做模糊搜索时，也是 `LIKE` 文本匹配。

### 2.6 仍待定

- [x] `recorded_at` 用秒还是毫秒精度？
  - **结论：毫秒。**
  - 理由：64 位下秒/毫秒存储空间无差异；毫秒能区分同秒内多次写入（如体脂秤批量录入 N 条、反向账单+正确账单几乎同时），秒级会撞上相同 `recorded_at`，导致 §9.11 "按 `recorded_at` 取最大值"无法区分先后。
- [x] JSON 在不同库的行为差异是否需要在应用层做一层封装？
  - **结论：不需要，因为根本不用 JSON 类型，直接 TEXT 存 JSON 字符串。**
- [x] `id` 字段用 `BIGINT` 自增还是 UUID？
  - **结论：UUIDv7。**
  - 理由：个人项目数据量小（年 ~1 万条、10 年 10 万条），UUID 的空间/索引性能缺点在此量级都不成立；
  - 多源天然不冲突（AI + 设备双来源）；
  - 10 年后大概率换系统（届时会有现成的带高效 memory 的原生 AI，不再用这套自建简陋系统），不为远期优化；
  - 跨库迁移友好。
  - **选 UUIDv7 而非 v4 的关键理由**：v7 是 time-ordered（毫秒时间戳前缀 + 随机尾），单字段同时充当 PK + 时间顺序，**可彻底砍掉 `recorded_at` 字段**。
  - UUIDv7 在 2026 年主流库/框架都支持生成（PG / Node 端均可），流行度足够。

### 2.7 砍掉 `recorded_at` 字段

**结论：`recorded_at` 字段从记录表移除，由 `id`（UUIDv7）兼任。**

**背景**：
- `recorded_at` 在本系统几乎无业务意义——大部分记录本就是追记（醒来才记昨晚几点睡、下班才记上班情况、学完才记学了什么）；
- 查询不对 `recorded_at` 过滤（§5.8）；
- `recorded_at` 的唯一业务用途是 §9.11 体征覆盖机制"同天多值取最新写入的那条"——需要一个能反映写入先后顺序的字段。

**砍掉方案**：UUIDv7 因其毫秒时间戳前缀，自然按时间排序，`MAX(id)` 即"最新写入的记录"。

**对 §9.11 的调整**：
- 体征覆盖取值规则原为"同一天多条记录时，先按 `happened_at` 取当天，再按 `recorded_at` 取最大值"；
- 改为"同一天多条记录时，先按 `happened_at` 取当天，再按 `id`（UUIDv7）取最大值"——UUIDv7 单调递增，最大即最新写入；
- 反向账单机制不依赖任何时间排序，无需调整。

**对字段表（§7.2 / 昨天文档）的影响**：
- 记录表字段变为：`id`（UUIDv7，PK）/ `happened_at` / `value_numeric` / `value_text` / `tags`（TEXT 存 JSON）/ `ai_comment` / `raw_time_text`。
- 字段数从 8 减为 7。

## 3. 部署分析：Vercel + Neon

> 暂停表设计，先讨论部署。如不行再换。

### 3.1 选型

- 应用层：**Vercel**（Next.js 原生部署，与 `.gitignore` 已确定的栈一致）
- 数据库：**Neon**（serverless PostgreSQL，原生支持 §2 的时间类型与 JSON）
- 协议：AI 与后端走 **HTTP POST**，放弃 MCP（见 §3.3）

### 3.2 契合度分析

| 维度 | Vercel + Neon 是否满足 |
| --- | --- |
| Next.js 栈 | ✅ Vercel 是 Next.js 原生平台 |
| PostgreSQL | ✅ Neon 是真 PG，`TIMESTAMP WITH TIME ZONE` / JSON / UUID 都原生支持 |
| 量级 | ✅ 免费够用：Neon 0.5GB + 60 compute 小时/月；10 万条记录 + 索引几十 MB；Vercel 函数 100 万调用/月 |
| 连接池 | ✅ Neon 自带 pooler，适配 Vercel serverless 的"短连接多"模式（serverless + PG 最易踩的坑） |
| 函数超时 | ✅ 免费 10s / Pro 60s；本项目接口都是"插一条记录"毫秒级，无压力 |

### 3.3 MCP 这条线放弃

- MCP server 通常是常驻进程，Vercel 是无状态 serverless，二者不匹配；
- 改走"AI 调普通 HTTP POST"，与昨天 §8 的"LLM 调 HTTP POST 到后端"一致；
- 即 LLM 端用 function calling，工具的实现是一个 HTTP 客户端调用 Vercel 上的 Route Handler，不需要常驻 MCP server。

### 3.4 可能踩到的坑

1. **后台任务**：将来若需要"每日自动统计推送给 AI"这类常驻 worker，Vercel 不能跑——需用 Vercel Cron（免费每天一次）或外挂。
2. **冷启动**：Neon 闲置后会 suspend 计算，下次查询有 ~1s 延迟；个人项目可接受。
3. **Vercel 函数无状态**：不能依赖进程内缓存、长连接；每次请求都是独立函数调用。

### 3.5 结论

**Vercel + Neon 可行，直接走这条。**

- 协议定为 HTTP（非 MCP）；
- 后端即 Next.js Route Handlers；
- 后续若发现 v1 后台任务需求膨胀，再考虑外挂 worker 或换部署平台。

## 4. 具体使用场景与动机

### 4.1 当前已走通的工作流

- 我与 AI 聊天，让 AI 记录信息；
- 目前 AI 把记录写到**本地 Markdown 文件**。

### 4.2 现在想做的事

把存储从"本地 Markdown"迁移到"HTTP → 数据库"。

### 4.3 迁移动机

1. **比文件好分析**：数据库有结构化字段（数值、时间、tag），可 SQL 查询、聚合；Markdown 要靠 AI 重新解析，成本高且不稳定（与 S7 同源问题）。
2. **容易做统计**：体重趋势、睡眠时长、时间分配等统计，在数据库里是简单 SQL；在 Markdown 里要么靠 AI 每次重新读，要么额外写解析器。

### 4.4 含义

- v1 的核心是"把已走通的 Markdown 记录迁移到 DB"，不是从零做新功能；
- AI 仍是唯一录入入口（见昨日 §8），只是写入目标从文件改成 HTTP；
- 用户侧体验不变，仍是和 AI 对话。

### 4.5 现有 Markdown 样本分析

> 样本：`2026-07-26.md`（用户提供）

**现有格式**
- 每行：`HH:MM - <内容>`
- 时间：记录写入时刻（对应 `recorded_at` 语义）
- 内容：AI 对 MDK 发言的转述/总结，非原文

**样本片段示例**
```
18:00 - MDK 说快到中午才起来，昨天睡太晚了，和小月黑白颠倒有关系。又一次印证了 lesson 4：小月的作息会拖垮他的睡眠。
18:38 - MDK 纠正：其实吃了不少——400ml 酸奶 + 400g 吐司。下午觉得冷的主因不是吃的少，而是长时间专注数学物理没动，身体处于低活动状态。我之前的判断偏了。
```

**与现有设计的差距**

| 维度 | 现状 | 设计要求（见 §1.8/§1.9/S7） | 差距 |
| --- | --- | --- | --- |
| 原文保真 | AI 转述/总结 | 约定逐字保真（§1.9，软约束） | ⚠️ 软约束，无法强校验 |
| 数值提取 | 埋在文本里（"400ml 酸奶"） | 抽到 `value_numeric` | ❌ 违反 S7 |
| tag | 无 | 应有内容 tag（学习/睡眠/社交…） | ❌ 缺失 |
| AI 评论 | 与事实混在一起（"我之前的判断偏了"） | ？未定义 | ⚠️ 待定 |
| 重复行 | AI 多次重新总结同一件事 | 一条记录一次入库 | ⚠️ 待定 |

**暴露出的新问题**

1. **AI 的评论/分析算不算"记录"？**
   - "值得肯定"、"我之前的判断偏了"、"纠正了我之前的判断"——这些是 AI 的衍生分析，不是 MDK 的事实；
   - 入库会污染事实层；不入库又丢失了 AI 的判断过程。

### 4.6.1 AI 评论字段：ai_comment

**结论：新增 `ai_comment` 字段（文本，可空），与 `value_text` 分列存放。**

- `value_text` —— 用户原始发言，逐字保真（§1.9）
- `ai_comment` —— AI 的评论/分析/判断，依附于同一条记录

**为什么单独字段而不是独立记录**：
- AI 评论总是依附于某条用户发言，强绑定关系；
- 拆成独立记录会让 AI 评论混进统计（如统计睡眠时长时把"值得肯定"也算进去）；
- 分列存放：查事实看 `value_text`，查 AI 分析看 `ai_comment`，干净。

**ai_comment 也逐字保真，不重新生成**：
- AI 评论同样是"那一刻的表达"，与 `value_text` 同等对待；
- 若 AI 理解错了，**用户说出来作为一条新记录 append**（遵循 §4.6 append-only），而不是让 AI 重新生成评论；
- 重新生成具有不确定性，append 新记录是确定且可追溯的。

> 一句话：原文与 AI 评论都保真，错误都靠 append 勘误，不靠重新生成。

### 4.6.2 一次发言拆不拆记录，由 AI 自行判断

**问题**：用户一次发言可能含多个不相关事实（如"睡到 9 点，晚饭吃了面条"），AI 该拆成多条还是记一条？

**结论：不硬性规定，让 AI 自己判断。**

- 允许拆：当发言里多个事实毫不相关时，AI 可拆成多条记录，每条打对应 tag；
- 允许不拆：当事实关联较紧或拆分代价过大时，AI 可记成一条，打多个 tag；
- 不写 hook 校验拆分粒度——与 §1.9 同性质，属 AI 自主范畴，用户控制不了。

**与已有设计的关系**：
- 不强制拆 ↔ 不强制合，二者并存，由 AI 根据语义自行裁量；
- 不引入 `parent_id` / 关联字段（违反 §7.5 能省则省）；
- 拆与不拆都不影响原文保真（§1.9）：拆的情况下，每条记录的 `value_text` 是该事实对应的用户原话片段；不拆则整段原话入库。

> 一句话：拆不拆是 AI 的判断权，不是 schema 约束。

## 5. 系统定位的重大转向：观察日志 + 无前端

### 5.1 重新定位

经过讨论，记录的本质重新定位为：

- **观察日志**：AI 与用户交流，观察其所作所为、所思所想，客观记录下来；
- **黑匣子**：用户几乎不会主动去读 DB 原文；
- **AI 是唯一读者**：所有查询、统计、分析，都通过 AI 转手——AI 查数据库 → 分析 → 用自然语言告诉用户。

### 5.2 含义

- **不需要前端 UI**：v1 可以无前端展示，用户交互全在 AI 对话里完成；
- 用户问题示例：
  - "上个月工作做了些什么？"
  - "今年来的体重趋势是什么？"
  - "最近的情绪是否稳定？"
- 这些都由 AI 查询 DB（SQL 或调用查询接口）→ 分析结果 → 自然语言回答用户。

### 5.3 对已有设计的影响

| 设计项 | 影响 |
| --- | --- |
| §1.8 原文冗余 | **仍成立**——AI 是读者，原文冗余让 AI 既能看衍生字段又能看原文，更准 |
| §1.9 逐字保真 | **仍成立**——前端要展示原文给用户看，逐字保真仍有意义；待磨合期后再考虑松动 |
| §4.6.1 `ai_comment` | **仍成立且更重要**——用户不读原文，AI 评论/上下文补全成为 AI 自己后续理解的依据 |
| §4.6 append-only | **仍成立** |
| §4.5 历史迁移 | **可降优先级**——既然用户不读原文，历史 Markdown 留着也无妨，新数据进 DB 即可 |
| 前端 UI | **v1 仍需**——至少能看原文，作为磨合期检视与调试用；待磨合完成后再考虑移除 |
| 查询接口 | **必做**——AI 需要能查 DB（按 tag、时间区间、数值范围等） |

### 5.4 v1 范围（修正）

原计划：录入接口 + 存储表 + 前端展示
新计划：**录入接口 + 存储表 + 查询接口 + 简易前端（看原文）**

- 录入：AI 调 HTTP POST，append 一条记录
- 查询：AI 调 HTTP GET（参数化查询）
- 前端：能看原文，最小化展示层（磨合期工具）

### 5.5 录入接口形态（按三类分）

**录入按语义拆成三个接口：**

| 接口 | 主要 payload | 用途 |
| --- | --- | --- |
| `POST /log/numeric` | `value_numeric` + tag + 时间 | 记录数值（体重、血压、心率…） |
| `POST /log/text` | `value_text` + tag + 时间 | 记录自然语言（行为、心情、思考…） |
| `POST /log/interval` | `happened_at` + `happened_until` + tag + 描述 | 记录时间段（睡眠、工作时段…） |

**为什么按语义拆而不是单一通用接口**：
- 每个接口参数更聚焦，AI 调用时意图明确，减少错填概率；
- 与"AI 录入受 schema 约束"（S7）一致：接口形态本身即在引导 AI 把数值塞数值字段、文本塞文本字段；
- 三个接口对应三种主要数据形态，与 §7.2 表字段设计一致。

### 5.6 查询接口形态（也按三类分）

**查询也对应拆成三个接口：**

| 接口 | 用途 |
| --- | --- |
| `GET /query/numeric` | 查数值类记录（按 tag、时间区间） |
| `GET /query/text` | 查文本类记录（按 tag、时间区间、全文关键词） |
| `GET /query/interval` | 查时间段类记录（按 tag、时间区间，含时长统计） |

**关键决策：不分专题视图给 AI**

- 否决方案：按维度建视图（`v_weight`、`v_blood_pressure`、`v_heart_rate`…），每加一个新维度都要建新视图；
- 选用方案：AI 自己用 tag 区分维度（如查体重就 `tag=体重`），不需要为每个生理指标单独建视图；
- 这与 §7.3 "一切皆 tag" 的取向一致——维度靠 tag 表达，不靠表/视图结构。

**表结构隐藏**：
- 三个查询接口都返回结果集，不暴露底层表结构与字段名；
- AI 看到的是"按 tag 和时间过滤后的记录列表"，而非 SQL schema；
- 用户对暴露表结构的顾虑由此化解。

### 5.8 查询接口时间过滤（已定）

**只对 `happened_at` 过滤，不对 `recorded_at` 过滤**。

**理由**：
- 用户查询诉求几乎都是"某天/某段时间发生了什么"，针对 `happened_at`；
- `recorded_at` 在本系统几乎无业务意义——大部分记录本就是追记：
  - 早上醒来才记录昨晚几点睡的；
  - 下班才记录上班情况；
  - 学完才记录学了什么。
- 既然记录都是事后补的，"写入时刻"几乎不被查询关心，没必要暴露过滤。

**时间参数格式**：
- 使用 ISO 8601 带时区字符串，与 `happened_at`（`TIMESTAMP WITH TIME ZONE`）字段类型一致；
- 例：`from=2026-07-01T00:00:00+08:00&to=2026-08-01T00:00:00+08:00`；
- 半开区间 `[from, to)`，任一端可省略；
- 不用 Unix 毫秒——`happened_at` 存的是带时区时刻，用毫秒会把时区信息压扁，与字段语义不一致。

### 5.9 tag 过滤：支持多 tag，仅 AND 语义

**结论**：

- 支持多 tag 过滤：`tag=工作&tag=学习`；
- 仅提供 AND 语义——命中记录需同时带所有传入 tag；
- **不提供 OR 语义**——若 AI 想要并集，多次调用各取结果再自己合并。

**为什么只 AND 不 OR**：

- AND 是更强语义，结果集更小，更聚焦；
- DB 端实现 AND 简单（每多一个 tag 加一个 `LIKE '%"tagN"%'` 条件即可，因 §2.5 的"tag 不含双引号"约束，每个 tag 都能精确匹配）；
- OR 在语义层做合并容易出错——比如两个 tag 的记录有大量重叠时，AI 在客户端做并集容易漏；
- AND 让 AI 拿到精确小集再自行做 OR 合并，比反过来（让 DB 算 OR 再交给 AI 处理交集）更不容易错；
- 这与 §5.7 "聚合让 AI 自己算"同思路——DB 只做简单确定的事，复杂合并交给 AI。

**实现**：

- `tag=工作&tag=学习` → SQL 等价于 `tags LIKE '%"工作"%' AND tags LIKE '%"学习"%'`；
- 单 tag 时退化为最简单的 `tags LIKE '%"工作"%'`。

### 5.10 不引入复杂过滤框架，不支持 value_numeric 范围过滤

**结论**：

- **不引入 PostgREST / Hasura / Supabase** 这类自动把表暴露成复杂过滤 API 的框架；
- **不支持按 `value_numeric` 数值范围过滤**。

**理由**：

1. 框架（PostgREST 等）的"任意复杂过滤"是以**暴露表结构/schema**为代价换来的，与 §5.6 "不暴露表结构"直接冲突；
2. 本项目就一张表、7 个字段，自己写几个 Route Handler 比引入框架还简单，框架是过度工程；
3. `value_numeric` 范围过滤几乎无实际诉求——常见查询都是"近一月体重记录"，按时间拉出来后 AI 自己筛数值即可；
4. 与 §5.7 "聚合让 AI 自己算"、§5.9 "OR 让 AI 自己合并"同思路——**DB 只做最简单确定的事，复杂处理交给 AI**。

## 10. 接口鉴权

### 10.1 背景

Vercel 上的 HTTP 接口如果不鉴权，任何人都能往库里乱写。个人项目也必须有基本保护。

### 10.2 方案：环境变量 token + CLI 包装

- **token 通过环境变量注入**（`DIGITAL_TWIN_TOKEN`），不硬编码在代码里；
- **AI 不直接调 curl**——AI 直接调 curl 会在命令行暴露 token；
- **包装成 CLI 工具**：AI 只发 JSON payload 给 CLI，CLI 内部负责加 token、发 HTTP 请求；AI 永远不接触 token 本身；
- **Web 前端访问也需要携带 token**——登录页面输入 token，存到 localStorage，后续请求自动带；
- 个人使用场景下，一个 token 就够——不需要多用户、不需要 OAuth、不需要权限分级。

### 10.3 含义

- CLI 工具是 AI 与后端的唯一桥梁，AI 永远不直接发 HTTP；
- AI 调 CLI 时只关心 payload（JSON），不关心鉴权细节；
- token 泄露风险低——只在环境变量和 CLI 内部，不出现在 AI 的对话或命令历史里。

### 5.11 查询接口能力总览

经过 §5.6-§5.10 的讨论，查询接口的能力边界已经清晰：

**支持**：
- 按 `happened_at` 时间区间过滤（ISO 8601 带时区，§5.8）
- 按 tag 过滤，多 tag 仅 AND（§5.9）
- 按 `q` 模糊搜索所有字符串字段（§5.7，全文 LIKE）
- 账单类专用查询带机械聚合（§9.5，§5.7 的例外）

**不支持（作为过滤条件）**：
- 按 `recorded_at` 过滤（§5.8，且该字段已砍）
- 按 `value_numeric` 数值范围过滤——`value_numeric` 仍会在查询结果中返回，只是不作为过滤字段
- OR 语义的 tag 过滤（多次调用由 AI 合并）
- 通用聚合（账单除外，AI 自己算）

## 6. 重新审视：是否需要时间段字段

### 6.1 反思过程

7/27 引入 `happened_until`（时间段）是为了支撑 S1（睡眠时长）、S2（时间分配）这类聚合统计；
7/28 决定聚合让 AI 拿原始记录自己算（§5.7）；
**那么时间段的字段也就没必要在 DB 里存了**——AI 完全可以从两条独立点记录合成时间段：

- 记录 1："昨晚 23:00 睡觉" → `happened_at = 23:00`
- 记录 2："今早 7:50 醒来" → `happened_at = 7:50`
- AI 读到这两条 + 同带 `睡眠` tag，自行推出睡眠时长 8h50m

### 6.2 结论：消除 `happened_until` 字段

- 所有记录都是**点事件**，schema 上不再有时间段字段；
- 数据源本来就是点式的（设备点式、AI 对话点式），时间段本就是事后补充；
- 录入侧简化：AI 不需要在录入时构造区间，只记一个时间点；
- 分析侧由 AI 合成：当统计时长时，AI 自行从相关点记录推导时间段。

### 6.3 对 §7.2（昨天文档）字段表的影响

- `happened_until` 字段**删除**；
- 记录表字段变为：`id` / `recorded_at` / `happened_at` / `value_numeric` / `value_text` / `tags`（JSON） / `ai_comment` / `raw_time_text`。

### 6.4 边界情况：天然时间段事件的处理

有些事件天然是"一段"而非"一点"，例："下午 2 点到 5 点学习数学物理"。

**结论：录成一条点记录，时间段信息留在 `value_text` 原文里。**

- `happened_at` 存开始时间（14:00）；
- `value_text` 存用户原话"下午 2 点到 5 点学习数学物理"；
- 不拆成"开始/结束"两条点记录——会丢失活动的整体性；
- 不保留 `happened_until` 字段——schema 保持最简。

**取舍**：这让"时长"成了 `value_text` 里的隐式信息，与 S7（机器可统计性）有冲突。但通过 §6.5 的"日总结"机制补回来。

## 7. 重大转向：以自然语言复盘为中心

### 7.1 不需要机器性统计与图表

经过反思，确认系统目标不是"机械性展示"：

- 不需要好看的花里胡哨图表、折线图（个别场景除外，见 §7.4）；
- 用户是认真生活的人，要的是**有意识地去复盘**；
- 复盘需要：自然语言 + AI 主动参与 + 多轮对话，而非一行 SQL 聚合一个数字。

### 7.2 层层递进的复盘体系

| 复盘周期 | 触发方式 | AI 读什么 |
| --- | --- | --- |
| 日复盘 | 用户主动（当晚或次日晨） | 当日全部明细记录 |
| 周复盘 | 周末 | 本周全部明细 |
| 月复盘 | 月末 | 本月明细，或本月所有周复盘 |
| 季/半年/年复盘 | 周期末 | **基于短周期复盘的记录再次复盘**，需要时才回拉明细 |

**关键**：长周期复盘不直接读半年明细——先读周/月复盘的记录，做"复盘的复盘"；若发现某点需深挖，再让 AI 拉对应时段的明细。

### 7.3 复盘结果也是记录

- 复盘产出的自然语言（含段落、含偶尔的数值），**作为一条记录入库**，与原始记录同表；
- 表里并存：原始记录、周复盘、月复盘、年复盘，乃至"复盘的复盘"；
- 靠 tag 区分，如 `["周复盘","2026-W30"]`、`["月复盘","2026-07"]`；
- 这与 §5.2"观察日志"定位一致——记录的就是"我"的所有表达，复盘也是表达。

### 7.4 value_numeric 仍保留（且扩展到账单）

虽然不做机器性统计，`value_numeric` 仍保留，且有明确使用场景：

- **体重**：每天/每隔几天称一次，存 `value_numeric`，直接拉出来画折线图是值得的（不是花里胡哨，是真实趋势）；
- **账单/开销/收入**（新增维度）：用户愿意让 AI 记录每天开销，如"中午快餐 15 元"；开销与心情、生活关联，也愿意和 AI 讨论节省、不该花的地方；
- 账单在复盘时也是一部分——周/月复盘时，开销分析是自然语言复盘的一个章节；
- **凡是天然与数值吻合的生活维度，都进 `value_numeric`**。

### 7.5 推翻的设计

- **§6.5 日总结任务砍掉**：
  - 不再凌晨自动跑、不再生成数值衍生记录；
  - 日复盘是用户主动触发的自然语言对话，不是定时任务；
  - 与 §5.7 "聚合让 AI 自己算"也不冲突——根本不做聚合了。
- **S1/S2 的真实需求重新理解**：
  - 不是 SQL 聚合出"月平均睡眠时长"；
  - 而是 AI 读一周记录后用自然语言告诉你"这周睡得怎么样"；
  - Stories 里的 S1/S2 应改写或加注释。

### 7.6 复盘记录的本质：就是一条带 tag 的普通记录

**关键澄清：复盘与其他记录没有任何结构上的区别，仅仅多一个 `复盘` 类 tag。**

- 周末晚上 7 点开始复盘 → `happened_at = 19:00`，这个时间点本身有意义（"我是在 7 点这个状态做的复盘"）；
- 复盘时的心情、状态也是记录的一部分——它不只是"回顾历史"，而是"正在发生的事情"；
- 内容会混合：
  - **历史性回顾**（这周发生了什么）
  - **对历史的评价**（这周工作做得好不好）
  - **当下的状态**（此刻的心情、此刻的思考）
- 这三类内容混在同一条记录的 `value_text` 里，由 AI 自然语言承载，不强行拆字段。

**推论**：
- 复盘记录不需要专门的字段或结构；
- 它就是一条普通记录，恰好 tag 是 `["周复盘","2026-W30"]` 而已；
- AI 在生成复盘内容时，自然地把历史回顾 + 评价 + 当下状态揉成一段文字，存入 `value_text`；
- §1.9 逐字保真的适用性：复盘内容的"原话"是 AI 产出的成段文字（不是用户原话），按 §7.6 的方式由 AI 整理生成即可。

### 7.7 已决项

- [x] 复盘记录的 tag 命名约定：`review:weekly` / `review:monthly` / `review:daily` 等，用 `review:*` 前缀 + 周期；
- [x] 复盘记录与原始记录**绝不关联**——写死这条规则，因为关联关系很难维护；
- [x] 体重折线图这类强数值化的内容，**做前端图表展示**。

### 7.8 已决项（续）

- [x] `review:*` tag **不带时间标识**：时间靠 `happened_at` 字段表达，tag 里带时间信息本身就不对（tag 是语义分类，不是时间索引）。

### 7.9 跨期复盘的检索（如 7 月复盘在 8 月才做）

**问题**：复盘的 `happened_at` 是复盘发生时刻（8 月初），覆盖的时段是 7 月，二者不同。

**结论：不为此加任何字段或语义，靠 AI 自行筛**。

- 复盘记录数相对全记录很少（月复盘一年 12 条，10 年 120 条），AI 全读再筛毫无压力；
- 通用查询 API 已足够：AI 用 `happened_at` 划定一个大致时间范围（如查 7 月底~9 月初之间、tag 含 `review:monthly` 的记录），再从结果中读 `value_text` 确认是"7 月复盘"；
- 复盘内容里自然会说"这是 7 月的复盘"或"这个月……"，AI 一读便知；
- 不污染 `value_numeric` 语义、不加字段、不破坏"tag 不带时间"原则。

### 7.10 前端 v1 / v2 范围划分

**v1 前端：记录表的 CRUD 界面**

- 目的：让用户**不用直接翻数据库**就能查看记录表全部内容，并做基础增删改查；
- 必要性：项目刚启动时，AI 会犯错、用户约束不足，磨合期需要用户主动删改很多记录；
- 与 §4.6 append-only 一致——append-only 是 AI 接口层面的约束，人一直可以直接改库；前端只是把"直接改库"变成"通过 UI 改"，降低门槛；
- v1 不做图表、折线图、可视化分析。

**v2 前端：图表与可视化**

- 体重折线图等强数值内容的图表展示；
- 复盘结果的可视化呈现；
- 等核心链路磨合稳定后再做。

## 8. 使用场景汇总（开发参考）

> 把两日讨论中散落的具体场景集中列出，便于后续开发对照。沿用 7/27 的 S 编号，新增 S8 起。

### 8.1 原始记录类场景

- **S3 体重趋势**：每隔几天称一次体重，存 `value_numeric`；前端（v2）可直接拉出画折线图，体重折线不是花里胡哨，是真实趋势。
- **S8 账单/开销记录**：每天开销进 `value_numeric`，如"中午快餐 15 元"。开销与心情、生活关联，复盘时一并讨论。
- **S9 开销讨论**：用户愿与 AI 讨论本月花销如何、有什么可节省的、有什么不该花的——基于原始账单记录做自然语言复盘。
- **S4 心情/情绪轨迹**：记录心情，按时间序列回看。
- **S5 行为回溯**：补记白天发生的事，能按"事件实际发生时间"检索。
- **S10 模糊时间记录**："昨晚 23 点睡"+"今早 7:50 醒"两条独立点记录，`happened_at` 塌缩为精确值，AI 后续读两条合成睡眠时长。
- **S11 天然时间段事件**："下午 2 点到 5 点学习数学物理"——一条点记录，`happened_at=14:00`，时长信息留在 `value_text` 原文，由复盘时 AI 读取。
- **S12 一次发言多事实**："睡到 9 点，晚饭吃了面条"——拆不拆由 AI 自行判断。
- **S13 回复式发言**：AI 问"下午工作还是学习？"用户答"工作"——`value_text` 保真存"工作"，`ai_comment` 补全上下文"AI 问下午工作还是学习，用户答工作"。
- **S14 即时录入**：用户说"工作差不多处理完了，我决定上午不再碰工作，先赶紧把单词给复习完"——典型一条点记录，多 tag（工作/学习/单词），AI 评论可补"主动保护学习时间"。
- **S24 账单强制拆分**：用户说"3 块钱买了可乐，吃了 12 块钱的鸡腿饭，可乐配鸡腿饭，味道真好吃"——必须拆三条：3 元可乐消费、12 元鸡腿饭消费、独立主观判断"可乐配鸡腿饭真好吃"。合并成 15 元会丢失分项粒度；主观判断混入账单条目会污染账目。这是 §4.6.2 "AI 自行判断拆不拆"的例外——账单类强制拆分。
- **S25 体脂秤批量录入**：体脂秤一次给出多项数值（体重、体脂率、脂肪含量、肌肉含量，以及手臂/躯干/下肢各自的脂肪与肌肉含量），每项独立记一行（各自可画趋势），但 AI 只调用一次 `/log/numeric/body_composition`，后端内部拆成 N 条入库。一次测量多项固定数值的场景都走这种批量模式（血压同理）。

### 8.2 复盘类场景

- **S15 日复盘**：当晚或次日早晨，用户主动触发；AI 读当日全部明细，与用户多轮对话；产出的自然语言作为一条 `review:daily` 记录入库。
- **S16 周复盘**：周末，AI 读本周全部明细；产出 `review:weekly` 记录；可能持续 10-20 分钟的多轮对话。
- **S17 月复盘**：月末（或下月初，如 7 月复盘可能 8 月初周末做），AI 读本月明细或本月所有周复盘；产出 `review:monthly` 记录。
- **S18 季/半年/年复盘**：基于短周期复盘的记录再做"复盘的复盘"，需要时才回拉明细；产出 `review:quarterly` / `review:halfyear` / `review:yearly` 记录。
- **S19 跨期复盘检索**：过了很长时间找"7 月的复盘"——AI 用 `happened_at` 划大致时间范围（7 月底~9 月初）+ `tag=review:monthly` 筛选 + 读 `value_text` 确认（§7.9）。
- **S20 复盘内容混合性**：复盘记录混合历史回顾 + 对历史的评价 + 当下状态心情——三类内容揉在 `value_text` 一段文字里，不拆字段（§7.6）。

### 8.3 标签/系统类场景

- **S6 标签管理**：tag 渐进创建、AI 自觉去重；"锻炼/workout"等异写通过用户人工全表 UPDATE 合并；提供"列出所有 tag"接口供肉眼检视。
- **S21 模糊搜索**：查"加班"等不会作为 tag 的关键词——`q` 参数对 `value_text` / `ai_comment` / tag 做模糊匹配。
- **S22 磨合期纠错**：项目初期 AI 易犯错、用户约束不足——用户通过 v1 前端 CRUD 界面主动删改记录。
- **S23 错误勘误**：单条事实层小错（一句话说错）——AI 不改原记录，新增一条勘误记录；影响统计的错误（如 tag 重复）——人直接改库（§4.6）。

### 8.4 已被重新理解的旧 Stories

7/27 文档中的 S1/S2 重新理解：

- **S1 睡眠时长统计**（原）：原想 SQL 聚合出"月平均睡眠时长"。
  - **重新理解**：真实需求是 AI 读一周记录后用自然语言告诉你"这周睡得怎么样"——属 S16 周复盘的子内容，不是独立 SQL 聚合需求。
- **S2 时间分配统计**（原）：原想 SUM(时长) GROUP BY tag。
  - **重新理解**：同上，是周/月复盘里"这周工作/学习/娱乐时间分配如何"的自然语言章节。

### 8.5 S7 仍有效

- **S7 数值提取的成本**：数值型必须有独立 `value_numeric`，不能与文本合并——保证体重、开销等可被机器读出画折线、查最新值。

## 9. 账单场景：机械化统计 + 强制拆分

### 9.1 场景描述

用户录入消费时，一段发言可能含多个独立消费项 + 主观感受，例：

> "3 块钱买了可乐，吃了 12 块钱的鸡腿饭，可乐配鸡腿饭，味道真好吃。"

**应拆成三条独立记录**：
1. `value_numeric=3` + tag `["消费","饮食","可乐"]` —— 3 元可乐的消费
2. `value_numeric=12` + tag `["消费","饮食","鸡腿饭"]` —— 12 元鸡腿饭的消费
3. `value_text="可乐配鸡腿饭，味道真好吃"` + tag `["饮食","感受"]` —— 主观判断

### 9.2 为什么必须拆（两条理由）

- **粒度**：合并成 `value_numeric=15` 会丢失"可乐 3 元、鸡腿饭 12 元"的分项信息，不符合记账要求；账单的统计价值在于分项，而非总额。
- **客观/主观分离**：
  - 消费记录是**客观发生的事实**（3 元买可乐，这是不可改的账目）；
  - "味道真好吃"是基于这次消费的**主观判断**；
  - 主观判断虽源于这次消费，但不应与记账条目合为一体——记账是客观的，感受是主观的，混在一起会让账单被感受"污染"，也让感受失去独立性。

### 9.3 这条挑战了两个已定设计

**挑战 1：§4.6.2 拆不拆由 AI 自行判断**

- §4.6.2 说"AI 自行判断拆不拆"；
- 但账单场景**必须拆**，不能交给 AI 判断——合并消费会污染账目；
- 修正：§4.6.2 的"自行判断"是**默认规则**，但特定类型（如账单）有**强制拆分规则**。

**挑战 2：§5.7 查询接口不做聚合**

- §5.7 决定"聚合让 AI 自己算"；
- 但账单是**典型的机械统计场景**——月度消费总额、按类别(饮食/交通/娱乐)汇总、按日趋势等，都是简单的 GROUP BY SUM；
- 账单数据量比行为记录更密（一天可能多条），AI 每次拉明细再算不必要；
- 修正：账单类提供**专用 API 与机械统计能力**，是 §5.7 的例外。

### 9.4 录入接口：分细，URL 路径承载语义

**用户取向：接口拆细，让 AI 一看 URL 就知道在记什么，省去 AI 自行判断语义的负担。**

**接口树**：

```
POST /log/numeric/{kind}    —— 数值类
  /log/numeric/bill          —— 记账（金额 + 消费类别 tag + 时间）
  /log/numeric/weight        —— 记体重
  /log/numeric/{...}         —— 其他数值类各自单独接口

POST /log/text/{kind}       —— 文本类
  /log/text/record           —— 通用文本记录，可传任意 tags（行为、感受、思考…）
  /log/text/review/weekly    —— 周复盘（语义在 URL 里写死）
  /log/text/review/monthly   —— 月复盘
  /log/text/review/daily     —— 日复盘
  /log/text/review/{周期}    —— 其他周期复盘
```

**设计要点**：

- **第一层按 numeric / text 分**：`numeric` 路径完全提供 `value_numeric` 字段，`text` 路径没有；
- **第二层按类型细分**：URL 即类型，AI 看到路径就知道语义，不必再自行判断该走哪个 tag；
- **`/log/text/record` 通用兜底**：走它时 tags 自由传，承接所有非复盘、非特定类型的文本记录；
- **复盘接口把周期写进 URL**：`review/weekly` 即代表周复盘，AI 调用时立即知道这条记录就是周复盘，省去 AI 想"该打什么 tag"的步骤（tag 仍可带，但 URL 已隐含 `review:weekly` 语义）；
- **录入接口按此结构扩展**：将来新增"记血压"就开 `/log/numeric/blood_pressure`，新增"记日记"就开 `/log/text/diary`，路径本身就是文档。

**与 §5.5、§9.4（旧）的关系**：

- 推翻了 §5.5 的 `/log/numeric` `/log/text` `/log/interval` 三大类划分；
- 落实 §9.4"按数值类型分接口"的取向，并扩展到 text 类（record + 各周期复盘）；
- `value_numeric` / `value_text` 字段仍是 schema 层的，但接口按 URL 细分，让 AI 调用更明确。

### 9.5 账单专用查询 API（机械统计）

**查询**：`GET /query/bill`
- 参数：时间区间、tag 过滤（按消费类别）；
- **提供机械统计**：
  - 总额 SUM
  - 按分类 GROUP BY tag SUM
  - 按日/周/月聚合

> 这是 §5.7"聚合让 AI 自己算"的**例外**——账单数据量密、统计需求机械、AI 每次拉明细再算无必要。

### 9.8 批量数值录入：体脂秤场景

**问题**：体脂秤一次测量会给出多项数值（体重、体脂率、脂肪含量、肌肉含量，以及手臂/躯干/下肢各自的脂肪与肌肉含量…），每项都该独立记一行，但**不应让 AI 为每项数值调一次接口**——十几项就要调十几次，开销大、易出错。

**结论：接口支持批量录入**。

例：`POST /log/numeric/body_composition`
- payload 一次性传所有项（因用户一直在同一台体脂秤测量，各项数目固定，可写死 schema）；
- 后端**内部拆成多条记录**写入 DB——每项一条，各自独立可查、可画趋势；
- 对 AI 而言是一次调用，对 DB 而言是 N 条 insert。

**设计要点**：

- 接口形态：**单次调用、内部拆分、多条入库**；
- schema 由具体场景写死——体脂秤的项固定，不必动态；
- 该模式可推广到其他"一次测量多项数值"的场景（如血压计同时给收缩压/舒张压/心率）。

### 9.9 接口模式小结

经过 §9.4-§9.8 的讨论，录入接口形成两类模式：

| 模式 | 接口示例 | 入库条数 |
| --- | --- | --- |
| 单项录入 | `/log/numeric/weight`、`/log/numeric/bill`、`/log/text/record` | 一条 |
| 批量录入 | `/log/numeric/body_composition` | 一条调用，内部拆成 N 条入库 |

**通用原则**：
- URL 路径仍承载语义（§9.4）；
- 单次事实的单一数值 → 单项录入；
- 一次测量产出多项固定数值 → 批量录入接口，内部拆分；
- AI 侧永远是"一次调用一件事"，不暴露"拆分"的复杂度。

### 9.11 不开修改接口：用"覆盖"与"反向"机制处理口误

讨论中考虑过为数值类口误开一个 UPDATE 接口（如体重说成 74.8 实为 74.3、账单 20 说成 30），最终**否决**，仍坚持 §4.6 append-only，不开 AI 修改接口。

**两类口误的处理机制**：

**1. 体征类（体重 / 体脂 / 身体成分）—— 覆盖机制**

- 口误后**再记一条正确值**即可，不需要改原记录；
- 统计时取"同一天的最终值"作为当天值；
- **取值规则**：同一天有多条记录时，先按 `happened_at` 取当天，再按 `id`（UUIDv7）取最大值（最新写入的那条）作为当天代表值；
- 即便过几天才发现口误，AI 录入时把 `happened_at` 写回那一天即可覆盖；
- 体征本质是"当天的状态"，多条并存取最新，语义自然。

**2. 账单类 —— 反向账单机制**

- 账单 20 说成 30 → 记一条 -30 的反向账单 + 一条 +20 的正确账单；
- 反向账单也是一条普通账单记录，`value_numeric` 取负值，tag 同类；
- 机械 SUM 自动平掉，不需要任何特殊字段或状态标识；
- 用户无需手动改库，AI 自己就能处理；
- 与 append-only 完全自洽——所有动作都是新增记录。

**结论**：

- 覆盖（体征）与反向（账单）两种机制覆盖了数值类口误的所有常见形态；
- append-only 不破，AI 修改接口不开；
- 不引入 `superseded_by` / `status` / 审计字段，schema 保持最简。

### 9.12 强相关主观描述可同行录入

数值类接口的 payload 允许带 `value_text`（自然语言附注），用于记录与该数值强相关的主观感受：

- 称体重 75kg → `value_numeric=75` + `value_text="体重又胖了，我想减肥"` —— 同行
- 买冰淇淋 8 元 → `value_numeric=8` + `value_text="价格 8 块钱真贵"` + tag `["消费","冰淇淋"]` —— 同行

**判断准则**：
- 主观感受**与该次数值记录强相关**（"针对这次称重/这次消费的即时反应"）→ 可同行存入该数值接口的 `value_text`；
- 主观感受**是独立判断/联想**（如"可乐配鸡腿饭，味道真好吃"——这是对两次消费的组合评价，不依附于单一数值）→ 单独走 `/log/text/record`，不混入账单记录。

> 体重"又胖了"属前者（紧贴这次称重），账单"味道真好吃"若是单次紧贴也可同行，但"可乐配鸡腿饭"属组合判断必须独立——§9.1 的例子正是这条线。
2. **历史 Markdown 是否迁移到 DB？**
   - **结论：不迁移。**
   - 原因：原文已丢失（现在存的就是 AI 转述），无法回填 `value_text` 为"用户原始发言"；强行迁移也只是把转述再写一遍，价值有限；
   - 历史数据继续放 Markdown，新数据进 DB，两套并存；
   - **追记功能天然支持**：`happened_at` 可由 AI 自由写入，本身就支持"今天补记过去的事"；
   - **重大事件可手动追记**：用户指着某条历史 Markdown，让 AI 整理后录入 DB——AI 完全能完成，无需专门的批量迁移接口。

### 4.6 记录只增不删改（append-only）

**原则：不向 AI 提供 UPDATE/DELETE 接口，AI 只能 POST 新记录。**

- AI 发现错误时，**不修改原记录**，而是**新增一条记录**，在 `value_text` 里用自然语言说明"上一条错了/实际是……"。
- AI 在后续读取/统计时，自行结合勘误记录理解真实情况，与人类看日记勘误的方式一致。

**例外：人类可以直接改数据库**

- 上述 append-only 是对 **AI 接口层面**的约束，不是数据库层面的硬约束；
- 当错误**会外溢影响统计**时（如 tag 语义重复导致聚合错乱），用户会**直接介入数据库**修正；
- 当错误**仅是单条事实层的小错**（如一句话说错了），则遵循 append-only，用新增勘误记录处理，不去改原记录。

**判断准则**：
- 错误影响范围仅限该条记录自身 → append-only，用勘误记录处理；
- 错误会污染跨记录的统计/聚合 → 用户直接改库。

**对其他设计的影响**：
- §7.3 标签改名/合并走全表 UPDATE：**仍成立**——这正是"会影响统计的错误"，由用户直接改库修正，而非 AI 通过接口操作；
- §1.9 原文逐字保真：仍成立（作为给 AI 的约定）——AI 不能改原文，但用户可以；
- 简化 AI 接口：录入接口只有 POST，AI 侧没有 UPDATE/DELETE。

> 关键澄清：append-only 不是"数据库永远不可改"，而是"AI 接口不提供改的口子"。人与 AI 的权限不对称。
