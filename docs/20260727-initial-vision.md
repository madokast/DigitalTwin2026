# DigitalTwin2026 初始设想

> 创建日期：2026-07-27
> 状态：草稿，边讨论边写
> 性质：个人项目

## 1. 项目定位

这是一个**个人项目**，所谓"数字孪生"，对象不是工业实体，而是**我自己本人** —— 对"我"进行数字化的孪生映射。

## 2. 孪生对象的范围

目标：尽可能接入"我"的更多维度。初步覆盖三大类：

- **生理 / 身体指标**
  - 心率、睡眠、步数
  - 身高、体重
  - （后续可扩展：血压、血氧、体温等）
- **行为 / 状态**
  - 每天做了什么
  - 心情、情绪
- **认知 / 心智**
  - 知识
  - 记忆
  - 偏好

> 不预设上限，存储设计需足够通用，便于后续持续接入新维度。

## 3. 数据形态

录入的数据主要有两种形态：

- **数值型**：如体重 = 70.5
- **文本型**：如"今天下午去跑了步"等叙事性记录

存储要能同时承载结构化数值与非结构化文本。

## 4. 关于时间字段

这是一个待深入讨论的点。粗糙想法如下：

- 单一时间字段，语义上更接近 `created_at`（记录写入时间），而非事件实际发生时间。
- 原因：常常在晚上 8 点才补记白天发生的事，`happened_at` 难以精确。
- 取巧做法：**精确时间字段只表达"记录时间"**，事件实际发生时间在文本里自行说明。

### 4.1 时间的三层语义（讨论后初步共识）

- `recorded_at` —— 必填，系统时间，绝对精确，表示"这条记录是何时被写入的"。
- `happened_at` —— 可空，能精确就填，不能就空，表示"事件实际发生的时间"。
- 文本里的自然语言时间 —— 原样保留在内容里，后续可由 NLP 解析回填到 `happened_at`。

### 4.2 时间 vs 时间段

事件可能是**瞬时**的，也可能是**持续一段时间**的。

例：记录"今天晚上 8 点到 9 点，我在和 AI 聊数字孪生项目的设计"——这就是一个时间段，而非一个时间点。

因此 `happened_at` 可能不足以表达，需要考虑：

- `happened_at`（单点）+ `happened_until`（结束点），两点构成区间；
- 或 `happened_at` 既可以是 instant 也可以是 interval（类型上区分）。

### 4.3 模糊时间

还存在模糊时间，如"今天下午"、"昨晚"：

- 候选 A：原样存字符串"今天下午"，不做解析；
- 候选 B：解析成区间，如 14:00~17:00；
- 候选 C：两者都存——原文 + 解析后的区间字段，便于检索。

### 4.4 待讨论

- [ ] 时间段是用"起止两点"还是"单字段区间类型"？
- [ ] 模糊时间采用 A / B / C 哪种？

## 8. 数据录入入口

### 8.1 总原则

**不存在人工表单录入**。所有录入来源只有两类：

1. **AI（大模型）**：用户与 LLM 自然对话，LLM 在对话中理解信息，自行调用 tools / MCP，把结构化（或半结构化）数据通过 HTTP 请求 POST 到后端，由后端 insert 到记录表。
   - LLM 不一定知道底层数据库 schema，只感知一个 HTTP/工具协议。
2. **设备**：可穿戴设备、传感器等，按约定的 HTTP 协议自动上报数据。

### 8.2 含义

- 录入"语言"是自然语言或设备协议，**不是表单字段**；
- 表单字段对用户完全隐藏，由 AI 把自然语言翻译成后端可接受的字段；
- 用户与系统的唯一交互面是**对话**；
- 因此 §7.4 关于"一条记录能否同时是数值+文本"的疑虑在录入侧自然消解——AI 自己决定如何拆分/合并记录，用户不关心。

### 8.3 待定

- [ ] LLM 与后端的协议形态：tools / MCP / 普通 HTTP POST？三者是否要并存？
- [ ] 设备上报与 AI 上报是否走同一套 HTTP 接口、同一张表？
- [ ] 后端是否做"语义校验"（如发现 AI 漏填 recorded_at / 字段类型不符）并回怼 LLM 重试？

## 7. 存储模型（初步）

### 7.1 是否分表

曾考虑：把"瞬时事件"与"持续时间段"分成两张表。
结论：**不分**，统一一张记录表。理由：

- 分与不分都能work，但分开会引入"录入时先判断类型、再选表"的负担，以及"跨表查询/统计"的复杂度；
- 统一表更通用，"是否是时间段"由字段是否为空来自然表达。

### 7.2 记录表字段（草案）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | PK | 记录唯一 ID |
| `recorded_at` | timestamp | 必填，系统写入时间（精确） |
| `happened_at` | timestamp | 可空，事件实际开始时间（可由 NLP 从文本解析回填） |
| `happened_until` | timestamp | 可空，事件结束时间；非空则该记录是"时间段"，为空则是"瞬时" |
| `value_numeric` | numeric | 数值型记录的值（如体重 70.5）；text 型留空。**不可省**（见 S7：保证机器可统计） |
| `value_text` | text | 文本型记录的内容；numeric 型留空。**不可与 value_numeric 合并**（见 S7） |
| `tags` | FK[] → tag | 标签外键数组；一条记录可挂多标签 |
| `raw_time_text` | text | 可空，原文中的自然语言时间（如"今天下午"），原样保留 |

### 7.3 标签存储（已收敛）

不建独立 tag 表，记录表中以 `text[]` 数组字段存 tag 名。

- 录入由 AI 完成（见 §8），AI 录入前可先查现有 tag 列表，自行决定复用/新建；后端不靠外键 + 唯一约束来管这件事。
- **不需要 `new_tag` 标志**，纯靠 AI 自觉去重；后端另提供一个"列出所有 tag"的接口，供用户肉眼检视是否存在语义重复，发现后再手动 merge。
- 改名 / 合并 / 删除：直接对全表 `tag` 数组字段做 UPDATE。
- 性能：每天 20-30 条、年 1 万、10 年 10 万条；全表扫描 + 数组展开在该量级无压力；不为远期数据量做优化。
- **设计取舍**：tag 数量应保持克制，不追求上百上千的细粒度标签；若细分需求膨胀到那个程度，应转用全文分词检索而非继续堆 tag。

### 7.4 仍待讨论

- [x] 是否需要"来源"字段（`source: 'ai' | 'device'`）？
  - 倾向：**不要单列**，复用 tag 机制。给来源一个带前缀的"元 tag"，如 `source:device` / `source:ai`，与内容 tag 同存在 `text[]` 里。
  - 收益：表更瘦、字段更少；与"一切皆 tag"的取向一致。
  - 取舍：tag 不再纯内容语义，混入"元数据 tag"，统计 unique tag 时需要过滤掉 `source:*` 前缀；可接受。
  - 前缀命名空间约定（待定）：`source:*` 是否够清晰？是否需要其他元 tag 前缀（如 `confidence:*`）？

### 7.5 设计取向：能省则省

本节记录一条贯穿全设计的原则：

- **不预置"看起来有用但其实低 ROI"的字段**。具体取舍：
  - 不存数值单位（如 kg / bpm）。
  - 不存可信度、置信度等元数据。
- **单位是否需要的判断逻辑**：
  - 一次性记录的数据，单位重要，但一次性数据本就缺乏统计含义，不必为它优化；
  - 反复出现的数据，单位可由历史记录与上下文推断（如 AI 看历史体重都在 65-75 区间，新录入 70 自然是 kg）；
  - 文本型记录本身常带语义化描述（"又长到 70kg 以上了"），单位已在内容里。
- **核心动机**：让系统尽可能简单，简化 AI 的录入工作——不要让 AI 每次都往记录里堆十几个字段/标签。

> **该原则有边界**：见 S7——简化不能以牺牲"机器可统计性"为代价。因此数值型必须有独立 `value_numeric` 字段，不能与文本合并。其他元数据（单位、置信度等）仍按本节省略。

### 7.4 仍待讨论

- [ ] `kind` 字段是否必要？也可不分 numeric/text，统一存到 `value`（字符串），数值型也以字符串入存、读出时再转型——更简单但损失类型约束。
- [ ] 一条记录能否同时是数值+文本？（如"体重 70.5，今早空腹"）
- [ ] 是否需要"来源"字段（手动录入 / 可穿戴同步 / AI 补录）？

## 6. Stories / 需求池

> 记录下来的故事与需求，不预设实现优先级，待后续拆解。

- **S1 睡眠时长统计**：统计过去一个月，平均每天的睡眠时间是多少。
  - 隐含：睡眠必须以"时间段"记录（入睡 ~ 醒来），或至少有起止点；否则无法算时长。
- **S2 时间分配统计**：统计每天花多少时间在 工作 / 娱乐 / 学习 上。
  - 隐含：行为记录需带"时间段"和"类别标签"（工作/娱乐/学习）；类别体系需定义。
  - 隐含：一条行为记录可能跨越多个类别，或一个时段内有多条记录，需考虑去重/合并。
- **S3 体重趋势**：记录体重（数值），看一段时间的变化趋势。
- **S4 心情/情绪轨迹**：记录心情，按时间序列回看。
- **S5 行为回溯**：补记白天发生的事，并能按"事件实际发生时间"检索，而非仅按"记录写入时间"。
- **S6 标签管理**：标签在使用中渐进创建，不能预先枚举；同名异写（健身/锻炼/workout）需收敛为同一概念；用户层的"改名"本质是合并（merge）——把一个 tag 名替换为另一个，全表记录的对应 tag 同步替换。
  - **存储方案（已收敛）**：不建独立 tag 表，直接在记录表里用 `text[]` 数组字段存 tag 名（如 `["工作","学习"]`）。
  - 一条记录天然支持多 tag，无需外表关联。
  - 改名/合并 = 全表 UPDATE 该 tag 名，开销可接受（见下）。
  - 性能预期：每天约 20-30 条记录，年增 ~1 万条，10 年 10 万条——全表扫描（包括 GROUP BY 展开数组）在该量级下无性能压力。10 年后大概率换系统，不为远期数据量做优化。
- **S7 数值提取的成本**：若把数值与文本合并成单一 `value` 字符串字段，AI 录入体重时可能写成 `"72kg"`，也可能写成 `"今天早上 8 点称的，体重是 72kg"` 一整段。
  - 当用户想统计"近一个月体重变化趋势"时，前者可直接正则/类型转换提取数字；后者却无法机械提取，必须再次调用 AI 来解析——每次统计都付一次 AI 成本，且不可控、不稳定。
  - 结论：数值型数据必须有独立的、机器可读的字段（如 `value_numeric`），与文本描述字段分离。AI 在录入时被约束把数值放进数值字段，叙事性内容放进文本字段。
  - 这条 story 反驳了 §7.5 的"能省则省"取向在数值/文本分离这件事上的过度应用——简化不能以牺牲"机器可统计性"为代价。
