# RFC 9457 改造后续优化候选清单

> 创建日期：2026-08-05
> 性质：候选清单。RFC 9457 problem+json 改造（S1-S4）完成后回顾，收集值得进一步优化 / 改动的点。逐项判定**做 / 不做**，判定后更新「状态」。

## 判定规则

- 改动不得改变 HTTP 契约（problem+json 形状 / key 顺序 / 文案），不得造成双端不一致。
- 每项「做」须有测试兜底；「不做」须记录理由，避免反复重提。

## A. Go 代码（低成本）

### A1. `writeJSON` / `writeError` 编码样板重复
- 位置：`faas/internal/httpx/server.go` `writeJSON`（~L187）与 `writeError`（~L200）。
- 问题：两处各自 `Set("Content-Type", …)` + `SetEscapeHTML(false)` + `json.NewEncoder().Encode`，仅 Content-Type 与 body 不同，样板重复。
- 建议：抽公共 `writeEncoded(w, status, contentType, body)`；`writeError` 只保留组装 `ProblemResponse` + `statusTitle`。
- 影响面：内部重构，无契约变化；单测覆盖两路径。
- 状态：✅ 已做（抽 `writeEncoded(w, status, contentType, body)` 内部 helper；`writeJSON` / `writeError` 仅传 Content-Type + body）

### A2. `withJSONErrorPages` 404 判断脆弱
- 位置：`faas/internal/httpx/server.go` `withJSONErrorPages`（~L126）。
- 问题：`strings.Contains(ct, "application/json") && !strings.Contains(ct, "application/problem+json")` 双条件枚举——`problem+json` 不包含 `application/json` 子串，被迫补第二条件；将来新增 JSON 类 media type 易漏。
- 建议：用 `mime.ParseMediaType(ct)` 解析后精确匹配（`mediatype == "application/json" || mediatype == "application/problem+json"`）。
- 影响面：内部重构，无契约变化；`TestJSONNotFoundAndMethodNotAllowed` 已覆盖 404 改写路径。
- 状态：待决

## B. 测试增强

### B1. Node 集成测试缺 Content-Type 断言
- 位置：`tests/api/routes.test.ts`（及 `probe.test.ts` / `json-body.test.ts`）。
- 问题：Go 侧 `TestAuthRequired` / 404 已断言 `application/problem+json`，Node 集成测试只断言 `detail` 与 status，未锁 Content-Type。
- 建议：在 1-2 处代表性用例（如 400、401）断言 `res.headers.get('content-type')` 含 `application/problem+json`。`src/lib/httperror.test.ts` 已有单测覆盖，此处补集成层锁契约。
- 影响面：测试新增断言，无代码变化。
- 状态：待决

### B2. 契约测试 key 顺序只查 1 个 fixture
- 位置：`tests/openapi/contract.test.ts`（~L264，`Error fixture key order`）。
- 问题：仅对 `error-unauthorized.json` 检查 `Object.keys` 顺序，其余 10 个 error fixtures 未覆盖。
- 建议：循环 `openapi/fixtures/error-*.json` + `db-probe-error.json` 全部断言 key 顺序 `success→title→status→detail`。
- 影响面：测试增强，无代码变化。
- 状态：待决

### B3. Go 测试断言样板重复（`assertProblemDetail` helper）
- 位置：`faas/internal/httpx/server_test.go`（33 处 `json.Unmarshal(rr.Body.Bytes(), &body)` + `body["detail"]` 断言）及其它 httpx 测试文件。
- 问题：错误响应断言样板重复；上轮「测试用 typed struct」讨论暂不做（保持 `map[string]any` 解析），此为本方向的轻量替代——只 DRY 样板，不引入 struct。
- 建议：抽 `assertProblemDetail(t, rr *httptest.ResponseRecorder, want string)`（内部 `json.Unmarshal` 到 `map[string]any` + `body["detail"]` 断言）；必要时再抽 `assertProblem(t, rr, wantProblem)` 校验 title/status/success。
- 影响面：测试重构，语义不变；建议批量替换 53 处 detail 断言。
- 状态：待决

## C. OpenAPI 可维护性

### C1. 错误响应两套并存
- 位置：`openapi/paths/*.yaml`。
- 问题：错误响应既有内联 `$ref: '../components/schemas.yaml#/Error'` + 内联 example，又有引用 `responses.yaml#/BadRequest` 等公共组件——本次改造时暴露的既有不一致。
- 建议：统一收口：400/401/404/413/500 全部 `$ref` `responses.yaml` 公共组件（各路径的差异化 example 可并入公共组件或用 `content` 覆盖）。
- 影响面：OpenAPI 重构；需 `openapi:lint` + `test:openapi` 回归；改动面较大（8 个 paths 文件）。
- 状态：待决

### C2. `ProblemResponse` 命名
- 位置：`faas/internal/httpx/httperror.go`。
- 问题：Go struct 名 `ProblemResponse` 与 OpenAPI `Error` schema、既有 `XxxSuccess` 命名族不完全呼应（可选改 `ErrorResponse`，与 OpenAPI schema 名一致）。
- 影响面：纯改名；测试不引用该 struct 名。
- 状态：待决

## D. 建议不做（理论性 / 既有，倾向保留现状）

### D1. 未知 status 的 `title: ""` 兜底
- 现状：双端对未知 status 均输出空 title（Go `StatusText` 返回 `""`，Node `STATUS_CODES ?? ''`）。
- 分析：实际仅用 6 个已知 status（400/401/404/409/413/500）+ 502/503（probe 路径），`statusTitle` 单测已覆盖已知集；空 title 属理论路径。
- 倾向：不做。若未来引入新 status，`statusTitle` 单测会先暴露。

### D2. 内部 `httpjson` / `logapi` 的 `{ ok: false, error, status }` 命名
- 现状：内部函数 Result 用 `error` 键，HTTP 层统一映射为 `detail`。
- 分析：api-layering §6 明确内部 Result 形状独立于 HTTP 契约；改名波及大量内部调用，收益低。
- 倾向：不做。

### D3. `bufferResponse` 全响应双缓冲
- 现状：`withJSONErrorPages` 将全部下游写入先缓冲再转发（404/405 改写需要）。
- 分析：既有设计（非本次引入）；大响应（export NDJSON）已走独立路径；改写仅 404/405，成功路径性能开销可接受。
- 倾向：不做。
