# Tags 增删接口设计（add / remove）

> 创建日期：2026-08-05
> 性质：记录「给已有记录按 id 增/删单个 tag」接口的设计讨论与定案，供实现与 OpenAPI 契约引用。
> 触发：AI 记录时没想好 tag，事后需按 id 补充；`docs/20260805-log-number-batch.md` 新需求节引出，独立成文。
> 定位：系统「修改 API 最终清单」两大操作之一（另一为 tag 归一化 normalize，见 `docs/20260805-tag-design.md`）。

## 需求

AI（或客户端）为**已有记录**增/删单个普通 tag——记录写入时未带/未想好 tag，后期补上（搜索辅助）；或误加后移除。入参：记录 `id` + 单个 `tag`。

## 鉴权档位（已定）

**ApiToken（非 admin 路径）**，如 `POST /api/log/tags/add`、`POST /api/log/tags/remove`。

- 先例：`POST /api/log/todo/transition`——「修改已有记录」但 AI 常态使用，走 ApiToken。
- 增删 tag 是**搜索辅助**（加/删普通 tag，非破坏性），AI 全权操作下应被信任；与全表归一化 normalize（admin 级破坏）性质不同。
- normalize 走 admin（AdminToken）；单条增删走非 admin（ApiToken）。

## 设计

```
POST /api/log/tags/add      { "id": "019f...", "tag": "workout:arm" }
→ 200 { success, id, changed, tags: { from: [...], to: [...] } }

POST /api/log/tags/remove   { "id": "019f...", "tag": "workout:arm" }
→ 200 { success, id, changed, tags: { from: [...], to: [...] } }
```

### 语义（定案）

| 项 | 规则 |
|---|---|
| 操作集 | **`add`（加）+ `remove`（删）**——AI 是唯一操作者，应被信任；正常软件均允许删 tag，过度不信任违背「AI 全权操作」前提 |
| 粒度 | 一次一个 id + 一个 tag（`tag` 单数，非数组） |
| `add` 语义 | **纯追加**，不改/不删已有 tag |
| `remove` 语义 | **纯删除**该普通 tag；保留前缀/状态 tag 禁止删（见下） |
| 幂等 + 告知 | add 时 tag **已存在** → 200 `changed: false`（from == to，完整 tags 返回）；remove 时 tag **不存在** → 200 `changed: false`。**一律 200，不报错** |
| tag 合法性 | `tag` 必须合法 tag 名（`isValidTag`：字母/数字/下划线/冒号、不数字开头等）→ 非法 → **400** |
| 保留前缀校验（add/remove 对称） | `body:weight`/`todo`/`transaction_entry`/`review` 前缀 **禁止加也禁止删**（聚合/状态机依据）→ 400（含 hint 指正专用路径）。**`time` 不入保留前缀**——时间模糊标注是 AI 自由发挥（可加可删、不强制、系统不内建语义），见 `docs/20260805-design-philosophy.md` §5 |
| 幂等边界 | 「幂等告知」仅针对**合法且非保留**的 tag（重复 add / 不存在 remove → changed: false）；**非法 / 保留 tag → 400**（此类 tag 永不落库，不存在「已存在」的幂等情况） |
| 响应结构 | **add/remove 共用同一结构体**：`{success, id, changed: bool, tags: {from: [...], to: [...]}}`——`from`/`to` 为操作前后**完整实际列表（含保留 tag）**，AI 由 diff 推断操作结果；**不加 `action` / `target` 字段**（冗余，diff 已隐含） |
| 待办状态 tag | `todo:in_progress` 等四态 tag 禁止删（状态机由 transition 管理）——已含在保留前缀校验内 |
| 类型兼容 | 由保留前缀校验天然覆盖，无需额外逻辑 |
| 批量 | 不支持（单 id + 单 tag；多 id 由客户端循环调用） |
| id 不存在 | **404**，完整告知 `record not found`（作用于任意记录，非待办专用；对齐 todo/transition 404 语义，但文案通用化——**新增文案**，不复用 `to-do not found`） |
| 并发（U2 CAS） | 业务层 `WithTx` 包住，Repository 收 tx 执行器：`UPDATE ... WHERE tags=旧值`；affected==0 时二次读区分——**id 被删 → 404**；**tags 被并发改 → 409**（`record tags changed concurrently, retry`，AI 重查后重试）。实现时若事务内再读亦可（FOR UPDATE 等价），事务边界统一在业务层 UoW |
| 未知键 | `Unknown JSON key: <name>` → 400（对齐全系统） |

**校验顺序（非法/保留 tag 零 DB 访问）**：未知键 → 400 → `id` 格式（UUID）→ 400 → `tag` **合法性** → 400 → `tag` **保留前缀** → 400 → 全部通过才进入业务层 **UoW**（`WithTx` / `db.transaction`）→ **Repository**（存在性 → 404；重复性 → changed:false；更新 tags）。参数错误一律在访问数据库前拦截（分层见「架构：UoW + Repository」）。

### 请求/响应 schema（草案）

```
TagsAddRequest:   // remove 复用（路径区分）
  required: [id, tag]
  additionalProperties: false
  properties:
    id:   record id (UUIDv7)
    tag:  单个合法 tag 名；拒保留前缀

TagsEditSuccess:   // add/remove 共用响应体
  required: [success, id, changed, tags]
  additionalProperties: false
  properties:
    success: true
    id:      记录 id
    changed: 本次是否真的变更（重复 add / 不存在 remove → false）
    tags:
      type: object
      required: [from, to]
      additionalProperties: false
      properties:
        from: 操作前完整 tag 列表（含保留 tag）
        to:   操作后完整 tag 列表（含保留 tag）
```

## 架构决策：UoW + Repository（定案 2026-08-05）

新接口采用 **UoW + Repository** 分层（业务层与 DB 隔离；全局架构定案见 [`docs/20260805-repository-architecture.md`](20260805-repository-architecture.md)）：

| 层 | 职责 | 校验（零 DB） |
|---|---|---|
| 业务层（draft / handler） | 参数解析；**tag 只校验合法**（`isValidTag`）+ **保留前缀校验**（`reservedTagError`）→ 400；**经 UoW 开事务**；组织响应 | 未知键、id 格式（UUID）、tag 合法、tag 保留前缀 |
| **Repository**（`attachTag(id, tag)` / `detachTag(id, tag)`） | 收 **tx 执行器**（UoW 内）；记录**存在性**（id 不存在 → 404）；**重复性**（已存在 / 不存在 → changed:false）；CAS 更新 tags | —（tag 入参已过业务层合法 + 保留校验） |

- **Repository 暴露领域语义方法** `attachTag(id, tag)` / `detachTag(id, tag)`（非 SQL 透传；DDD 命名，业界常识）。
- **事务由业务层经 UoW 管理**（DDD 规范：事务边界是 UnitOfWork 的职责，不在 Repository）：Go `WithTx(ctx, pool, fn(tx))` / Node `withTx(db, fn(tx))`，Repository 方法统一收 tx 执行器（签名与只读方法一致，无割裂）。
- **事务保护并发（U2 CAS）**：业务层 `WithTx` 包住，Repository 内解决两种并发情况——**id 不存在**（404）与 **tags 被并发改**（`UPDATE ... WHERE tags=旧值` 冲突 → 409 或事务内再读，实现时定）。
- **Node 侧对称**：`@/db` 单例背后抽 repository 执行器接口，测试注入 fake executor（见 `docs/20260805-repository-architecture.md`）。

## 通知（定案 2026-08-05）

- **触发**：**仅 `changed: true`**（2xx 且确有变更）时，响应返回后触发（best-effort，notify 失败不影响响应；对齐 `SUPPRESS_BOT_NOTIFICATION`）。`changed: false`（幂等无变化）**不触发**。
- **格式**（含四要素：id / 动作 / 目标 / 变化，对齐 notify `key: value` 行风格）：

```
Tags updated
id: 019f...
action: add
tag: workout:arm
tags: from [exercise] to [exercise, workout:arm]
```

- 双端 `notifyTagsEdited` / `NotifyTagsEdited`（notify.ts / notify.go）。

## 与批量接口的关系

- **无耦合**：批量接口（`log/numbers` / `log/transactions`）**不回传 ids**，补 tag 也不依赖批量 ids。
- 补 tag 定位：**任意记录 + 任意时间的搜索辅助**——唯一目的是让记录可被后续搜索/聚合命中；AI 用 `query` 按条件搜回 id 后补 tag。
- 补 tag 不设时间窗口（无 created_at 字段，且「搜索辅助」语义不需要限窗）；所有记录类型（text/numbers/todo/review/transactions）均可补普通 tag（保留前缀除外）。
